## 0. 一句话结论

V1.0 是"控制台找设备、设备出码、多场景可叠加"；V2.0 是"控制台出码、设备输码、单场景互斥、显示端纯执行"。老师的心智从"管理设备"变成"上课放内容"——**设备在 V2.0 里退化成不可见的基础设施**。

## 1. 逐条变更（C1–C7）

### C1 控制端去列表、单终端直入

| 项 | V1.0 | V2.0 |
|----|------|------|
| 设备列表页 | `/#/devices`（设备卡片、在线状态、当前控制者、解绑） | **删除**。无列表页，无"先选设备再进入" |
| 登录后落点 | 登录 → `/#/devices` → 选设备 → `/#/console/:deviceId` | 登录 → **`/#/console`** 直达 |
| `:deviceId` | 路由必带 | **去掉**。保留 `/#/console/:deviceId` 仅作旧链接兼容，解析后立即 `replace` 到 `/#/console` |
| 在线终端 | 每张设备卡片一个在线点 | 顶栏一个只读指示：**"当前 N 个终端在线"**，不可点、不是导航入口（`aria-live="polite"`，N 变化时朗读） |
| 组件删除 | `DeviceCard`、`DeviceStatusCard`、`EmptyState`（无设备分支） | 保留 `EmptyState` 仅用于预选清单为空 |

**为什么顶栏只给一个数字**：老师上课不关心"是哪台"，只关心"投出去有没有人收到"。N=0 才需要行动，见 §6 兜底。

### C2 配对方向反转：控制码由控制台出、显示端输入

| 项 | V1.0 | V2.0 |
|----|------|------|
| 出码方 | 显示端 `POST /devices/register` 拿 6 位设备码并展示 | **控制台**生成并常驻展示**控制码** |
| 输码方 | 控制台 `DeviceCodeInput` → `POST /devices/bind` | **显示端**输码 → 绑定 |
| 显示端配对页 | `/#/pair`：大号 6 位码 + 二维码 + "开始使用"按钮 | **删除**。显示端首屏即输码页，无二维码 |
| 二维码 | 显示端展示，内容 `?code=XXXXXX` | 如保留，**放控制台侧**（内容为 `https://cds.242500.xyz/display.html?code=XXXXXX`），扫码即可带入；显示端不展示 |
| 有效期 | 30 秒刷新（PRD 3.2 / api.md 4.1） | **15 分钟 TTL + 单次消费**（CO-2026-11-18-02 修正，见 C2-3）。刷新即作废旧码，已绑终端不掉线 |
| 一码几端 | — | **一台一张码**：绑定成功即作废；要接第二台屏幕，刷新出新码。多终端镜像 = 多张票据（见 C2-2） |
| 术语 | 设备码 | **控制码**。全文统一，代码里用 `controlCode`，禁用 `deviceCode` 表示它 |

**交互口径**：控制码在控制台顶栏常驻（投屏前一眼可见），字号 ≥20px、等宽字体、可一键复制；无终端在线时升格为卡片（引导语："在教室屏幕输入此码"）。手动刷新后旧码立即失效，已绑定的终端**不掉线**（刷新只影响新接入）。

**显示端绑定后的缓存**：`localStorage.cds.controlCode`。启动逻辑：有值 → 直连；为空 → 只显示输入框（C5）。绑定成功后同一手势内解锁音频（C6）。

#### C2-2 一码多端 vs 一码一端（已按 Chief 修正收敛）

> **11-18 修订**：Chief 用穷举测算否掉了"长期有效"（6 位码 10^6 空间，10 次/秒可一天内约 58% 命中）。因此原"一码多端 + 长期有效"的组合作废，改为**单次消费 + 15 分钟 TTL**，一码一端；多终端靠**一台一张码**满足，顶栏计数不变。下面保留原始分析，作为决策依据的留痕。

Jeremyzh 点了"A 多屏镜像"，Chief 的假设 B 又写"一码绑一个显示端"，两条**互相冲突**：
- 若真"一码一端"，控制台永远只有 N=1，"当前 N 个终端在线"这个指示就是死代码；
- 若真"多端镜像"，就必然是一码可被 ≥2 台显示端同时使用。

**最终口径（2026-11-18 10:20 后）**：单次消费的码不可能一码多端，因此定为 **一码一端**；控制台需要接第二台屏幕时点 `⟳` 生成新码（旧码作废、已连终端不动）。N 台在线的诉求由"多张票据"满足，界面仍是"当前 N 个终端在线"，不需要设备列表——这一点比"一码多端"更安全，也不用改交互。

#### C2-3 控制码的时效、消费与格式（新增，CO-2026-11-18-02）

| 项 | 口径 |
|----|------|
| TTL | 15 分钟；**控制台顶栏倒计时是唯一可靠来源**。显示端输码页的“剩余 xx:xx”只是原型演示（同源 localStorage 模拟），**真机拿不到** —— 见 §5.1 异议 4 |
| 消费 | 绑定成功即作废（`used`）；刷新即作废（`revoked`）；到期作废（`expired`） |
| 限流 | 边缘按 **IP** 10 次/分钟（不能按码限流：攻击者猜的是不存在的码，没有行可累加）；超限一律回"控制码无效或已过期"，不泄露码是否存在 |
| 格式 | 6 位数字（默认）/ 8 位 Base32（空间 32^8≈1.1e12，抗枚举强约 100 万倍）；取决于显示端有无键盘 |
| 文案 | 过期：「控制码已过期，请在控制台刷新后重新输入」；失效/撤销：「控制码已失效，请重新输入」——两者必须分开，老师据此判断是刷新码还是重输 |
| **前置否决** | 显示端若是**无输入设备**（电视棒/纯投屏器），输码方向整体不成立，C2/C4/C5/C6 全部要回退；已上报 Jeremyzh。**退路（建议，不退回旧方向）**：控制台出一次性部署令牌 `POST /display-token`（7 天、绑一台），运维装机时打开 `display.html?token=…` 一次烧进 `localStorage`，之后长期免输码——日常上课与现设计完全一致，只是“首次配对”从老师做变成装机人员做。建议同步给运维，在交付清单加一条“首次装机配对” |

### C3 三场景互斥 + 提前预选

| 项 | V1.0 | V2.0 |
|----|------|------|
| 场景模型 | 音乐/文章/投屏可叠加（D-04） | **同一时刻只有一个**：音乐 \| 文章 \| 板书 |
| 切换方式 | 左右分栏并存 | 顶部分段控件（三段胶水式 Tab），点击即切，**无刷新、无白屏**（内容区 `opacity/transform` 交叉淡入 ≤180ms，DOM 不 teardown） |
| 状态保留 | 只有投屏结束要还原 L1 | 切回**必须**还原：音乐进度（`positionMs` 不丢，重新 `resume`）、文章滚动位置（`anchorVerseSn` + `scrollTop`）、板书草稿 |
| 音乐场景 | 边看边听 | 切走即 `pause`（不是 stop/卸载），切回 `resume` 到原位置 |
| 预选区 | 无（列表即播放列表） | **音乐、文章各有"今日预选"有序清单**：进控制台就能挑好今天内容排好序，使用中点条目即播/即读，**中途不搜索** |
| 搜索位置 | `MusicSearchBar` 在主控台常驻 | 搜索**只在预选编辑态可用**（点"添加"时出现），使用时列表只读 |
| `fullScreen` | `cast.start` 带 `fullScreen`，false 时左窄栏+右板书 | **作废**。互斥后板书场景独占全屏，字段不再下发（M1 见 §4） |
| 控制台"投屏中音乐继续" chip | 有 | **删除**（并存不存在了） |
| `MiniPlayerBar`（显示端文章阅读时显示音乐条） | 有 | **删除**（文章场景下音乐必须停） |

**"提前预选"的最小模型**（不新增服务端表，先用设备/用户级持久化）：
- 清单 = 有序 `items[]`，每项 `{musicId | (volumeId, chapterSn), note?, done?}`；
- 顺序可拖拽 / 上下移动；使用中点任一项 → 该场景激活并从该项开始，**当前项高亮**，下一项为"下一个"按钮的默认目标；
- 清单持久化：`localStorage.cds.preselect.{scene}`，登录后按用户合并（服务端持久化列为 P1，见 §5 异议 3）。

### C5 兜底：码失效必须能回输码页

V1.0 没有这条，会现场翻车（大屏黑屏无人能救）。V2.0 定为**硬需求 P0**：

| 触发 | 显示端表现 | 恢复 |
|------|-----------|------|
| 收到 `ack code.invalid` / `code.unbound` | 内容层淡出 → 输码态，提示条**「控制码已失效，请重新输入」** | 直接输新码 |
| 控制台点"全部解绑"/换控制台 | 同上（推送 `code.revoked`） | 同上 |
| MQTT 断线且重连失败 | 系统层黄条「与教室网络断开，正在重连…」+ 保留最后一帧内容（不黑屏） | 自动重连；连续失败 60s 后降级为"显示控制台最后下发的画面 + 重连提示" |
| 显示端本地码存在但被服务端判定无效 | 输码态 + 上述提示 | 同上 |
| 主动重置 | — | 输码态下：**长按屏幕 3 秒** 或 URL 加 `?reset=1` → 清 `localStorage.cds.controlCode` 并停在这里 |

"隐藏重置"必须在首屏**可发现但不显眼**：右下角 12px 灰字「长按 3 秒重置」常驻（现场老师能自救），长按有 3 秒环形进度反馈。

### C6 自动播放：绑定 + 解锁合并到同一个手势

V1.0 靠配对页"开始使用"按钮解锁。配对页没了，V1.0 的解锁点在 V2.0 里**不存在**，必须重写：

**输码 → 点"确认" → 同一个 click 手势内依次完成：**
1. `new AudioContext()` + `resume()`（`await` 不得跨 `await` 断开手势链，所以先同步创建）；
2. 创建一个**静音**的探测 `Audio` 元素（`src` 为空时 `muted` 播放 `data:` 空音频，或直接 `audio.play().catch()` 探测），确认 `autoplay` 未被拦；
3. 同一手势内发起绑定 `POST /devices/bind`；
4. 绑定成功 → 写 `localStorage` → 切内容层（此时音频上下文已解锁，首条 `player.play` 必定出声）。

失败分支：
- 绑定失败（码错/过期/被撤）→ 留输码态，错误内联在输入框下，**不弹窗**；
- 音频被拦（`NotAllowedError`）→ 仍进内容层，`SystemLayer` 显示「点击屏幕任意位置启用音频」；任意一次触摸补一次 `resume()` + `ack{ok:false,code:4002}` 告知控制台；
- 现场部署仍要求浏览器 `--autoplay-policy=no-user-gesture-required` 兜底（转运维，V1.0 §10.6 第三条保留）。

**验收口径**：输码进入后，控制台第一条 `player.play` **必须直接出声**，不允许出现"投了没声音"。

### C7 交付形态

- 11-20 前：控制台一屏原型 + 显示端两态原型（自包含单页，CSS/JS 内联，不引外部 CDN，符合发布链要求）；

## 3. V1.0 自身的三处内部不一致（本次顺手修掉）

1. **绑接口名不一致**：V1.0 §3.1/§7.2/§8.1 写 `POST /devices/binding`，而 `api.md` 4.2 是 `POST /devices/bind`。V2.0 全文统一按 `api.md`。
2. **`state.report` 与互斥冲突**：V1.0 允许 `nowPlaying` 与 `viewing` 同时非空。V2.0 要求服务端在任一时点只有一域非空，另两域为 `null`（否则控制台无法判断"现在到底在放什么"）。
3. **`fontScale` 双通道**：V1.0 里 `fontScale` 既在 `article.navigate` 里带，又在 `display.style` 会是全局设置。V2.0 归一为：**全局样式走 `display.style`，`article.navigate.fontScale` 保留但仅作"本章临时放大"且优先于全局值**。

### 5.1 四条异议/纠偏（我按自己的判断画了原型，若不同意请回一句，我改）

**异议 1｜"一码绑一个显示端"与"多终端镜像"自相矛盾。**
**已按修正方案关闭（11-18 10:20）**：改为**一码一端 + 单次消费**，多终端由"多刷一张码"实现。这样既能防枚举，也不会让 N 计数变成死代码。原"一码多端"方案作废，保留结论：不需要设备列表。

**异议 2｜互斥缺少服务端仲裁接口，`api.md` 里没有。**
"同一时刻只有一个场景"如果只由前端拼，会出现两类现场问题：两台控制台（或一台断网重连）各自以为自己是唯一；MQTT 断开降级时 `state.report` 与 REST 顺序错乱。建议开发在 API 变更里加**一条**场景仲裁：`POST /control/scene { deviceId, scene, payload }`，服务端持单条 session 状态并保证"旧场景先停、新场景再起"，`state.report` 只回一个 `scene` 字段。我这边原型按此假设画，接口名可改。

**异议 3｜"预选清单今天挑好"需要落库，否则换手机/第二天就丢。**
`localStorage` 只能保证同一台设备同一个浏览器。建议 `preselect` 作为用户级资源入 API（`GET/PUT /preselect/{scene}`，数组 + `updatedAt`），与 `playlists` 并列。P0 先做音乐（点条目即播），文章预选 P1 可先只存本地。我不改 api.md，登记给开发。

**异议 4｜“显示端输码界面显示剩余有效期”在真机上做不出来。**
显示端在按「确认」之前不知道要输哪个码；服务端也不能提供“按码查状态 / 查有效期”的接口——那等于免费的猜码预言机，正是 IP 限流要堵的洞。原型里能看到「剩余 12:40」，是因为控制台与显示端开在同一个浏览器、共用 `localStorage.cds.codeObj`。**这个捷径不能进实现**：禁止为此新增 `GET /control-code/{code}` 之类公开接口。
两个可行解，二选一：
- **A（按这个做，默认）**：倒计时只在控制台（挨着 `⟳`，老师要刷新时一眼看得见）；显示端输码页放一行**中性提示**「控制码 15 分钟内有效，过期请在控制台点 ⟳ 刷新」，提交后按服务端 `reason` 给文案（`expired` / `used` / `invalid` / `rate_limited`）。
- B：控制台出二维码，码里带 `code` + `expiresAt` + 一次性 nonce，扫码带参进入——这时显示端才知道有效期，可以真倒计时，还顺带省手输。代价：二维码 + nonce 校验，属 P1。
- 备注：`reason` 区分 expired/used 会弱泄露“码是否存在”（每次尝试 1 bit），在每 IP 10 次/分钟下可接受；开发若不愿承担，统一回「控制码无效或已过期」，代价是老师得自己想到去刷新。
