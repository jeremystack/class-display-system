### 3.1 但 §10.6 不能全删空——留一条架构约束

删掉"怎么做 autoplay"是对的；**不能连"声音从哪出"也不写**，否则下一次有人看到"显示端放歌词没声音"会当 bug 处理。V2.1 §10.6 改为一段「音频锚点」，核心三条：

1. 声音只从**控制页所在设备**出；display 永不发声。
2. 控制页跑在哪台设备，就要求那台设备接了场地音响（笔记本线路输出 / 单屏模式的 HDMI 回传 / 蓝牙）。
3. 移动端控制页锁屏即静音（浏览器行为，不可绕过）→ 现场用手机控制时，音乐场景默认不可用。

### 3.2 §5.1 异议：这是我唯一真正担心的一条（请 Jeremyzh 确认）

⑤ 在"显控一体"下成立且最自然；在"手机控制 + 教室大屏"下**物理不成立**：

| 部署形态 | 控制页设备 | 教室声音从哪出 | ⑤ 是否成立 |
|----------|-----------|---------------|-----------|
| 显控一体（HDMI 复制，单屏模式） | 同一台电脑 | 该电脑 → 投影/外接音响 | ✅ 最自然 |

## 4. 逐条详设

### 4.1 音乐：跨文档时基（⑤ 的实现核心）

control 页持 `<audio>`；display 只做"歌词跟随"，因此需要一条**不依赖消息频率**的时基：

```
player.play  { trackId, audioUrl, positionMs, durationMs }
              ↑ 不带任何时间戳（V2.1.1 删除 startedAtEpochMs，理由见下）
```

- display：`t0 = performance.now(); base = positionMs + delayMs; pos(t) = base + (performance.now() - t0)`，`rAF` 推进高亮，**不逐行下发**（每秒多次消息会打爆单连接）。
- `delayMs` 由控制页单侧测：发 `play` 记 `sendT`、收 `ack` 记 `recvT`，单程 `= (recvT - sendT) / 2`；取**最近 3 次的中位数**并 clamp ≤300ms，首播无样本取 0（V2.1.3：单次采样在教室 Wi-Fi 抖一下就能把歌词推后约 1s）。
- **为什么删掉 `startedAtEpochMs`（V2.1.1）**：服务端打点只消掉「控制台↔服务端」钟差，**消不掉「显示端↔服务端」钟差**。`positionMs + (Date.now() - startedAtEpochMs)` 用的是显示端的钟，而 D-1 的电视棒/盒子没有 NTP，钟可差几十秒到几分钟并随校时跳变 → 歌词整段跳或一路爬。开发机同机同钟，这个错**在本地永远测不出来**。残余误差只剩「服务端→显示端」单程延迟（一次性、10–100ms），不累积，靠 5s 重锚吸收。
- 页面重载后 `performance.now()` 归零，**不得续用旧 `t0`**：必须先 `GET /devices/{id}/state` 取当前 `positionMs` 再重锚。
- 校正：**下行 `player.sync`** 每 5s 一条（音频宿主＝控制页发、服务端转发），带 `positionMs/durationMs`；display 收到算 `Δ = (positionMs + delayMs) − pos(now)`，按**三档死区**处理（V2.1.7 修正方向：原句写「`state.report` 报一次」是错的——`state.report` 是 display→服务端**上行**，display 收不到自己的 report，拿它纠漂 `Δ` 恒为 0。V2.1.3）：`|Δ| < 80ms` 忽略；`80–300ms` 慢追（每帧靠 10%、单帧 ≤5ms）；`|Δ| > 300ms` 直接跳。口径以正文 §10.6 第 3 条为唯一来源，200ms / 250ms 两种旧写法作废。
- 暂停/续播：`playing:false` 冻结高亮行；`resume` 带新的 `positionMs`（不带时间戳），display 收到即重锚。
- **同一 origin 只允许一个音频锚点**（防双窗回声、防 console 与 `#/screen` 同时解码）：
  - `localStorage.cds.audio.lease = { owner, ts }`，owner 每 2s 心跳，3s 未续视为过期；
  - 抢不到的一侧**静音跟随**，控制条显示「另一窗口正在播放，此处静音」；
  - 这一条不做，现场症状是"投了有回声/两轨错位"，极难查。
- 移动端：`visibilitychange → hidden` 即 `pause` 并记位置；回前台**不自动续播**（防止教室突然出声），提示「已暂停，点播放继续」。

### 4.2 单屏模式（⑥）：新页面，不是新控件

**结论：同意 Chief —— 控件绝不进 `display.html`。** 理由补两条：display 只持设备级凭据（无控制权），加控件＝提权；且会出现"设备凭据 / 用户 JWT"两套鉴权分支，安全评审必挂。

| 项 | 设计 |
|----|------|
| 路由 | `/#/screen`（console 域，JWT 鉴权，需登录） |
| 布局 | 全屏渲染面（与 display 同一套 scene 组件）+ 底部**迷你控制条**（≤6 个控件） |
| 迷你控制条 | `待机 · 音乐 · 文章 · 板书`｜`⏮ ⏯ ⏭`（音乐）｜`上一屏 · 下一屏`（文章）｜`黑屏`｜`退出单屏` |
| 鉴权 | **不需要控制码**（同账号同机）。需 `POST /session/single` 用 JWT 换一条本机设备凭据，供 `state.report` / 心跳使用（§6-1） |
| 与多屏共存 | 同一账号可同时开单屏页 + 教室屏；两处渲染同一 `scene`；**音频只在单屏页**（它是控制页） |
| 隐藏 | 控制条 3s 无操作淡出至 12% 透明度，鼠标移至底边 80px 唤回；键盘 `Esc` 唤回；不设常驻按钮 |
| 退出 | 退出即回 `#/console`，**不**自动解绑设备凭据（下次进来直接用） |

**渲染器复用**：`src/display/scenes/*` 提升为 `src/shared/render/*`，由 display 与 `#/screen` 共用。禁止复制一份——否则"投影上排出来和预览不一样"，分页也会算错。

### 4.3 §5.2 异议：复制模式下控制条**学生会看到**（这条必须在文档里说破）

- 显控一体 = **HDMI 复制**（镜像）→ 投影上是老师屏幕的逐像素副本，**包括迷你控制条、包括你点"黑屏"的那一次点击**。
- 因此：
  1. 「黑屏」的真实作用是**不让学生看到下一条内容**（老师在本机准备下一篇经文时先黑屏），**不是防窥**；不能承诺"学生看不出老师在操作"。
  2. 控制条必须做**小 + 淡出**，且默认半透明 12%（宁可老师自己看不清，也别在大屏上刺眼）。
  3. 若老师确实需要"学生看不到我的操作"→ 只能**扩展模式 + 手机控制**（= 多屏模式），而那条路又回到 §3.2 的音频矩阵（手机不出声）。这两个诉求在物理上互斥，选一个。
- 设计意图段（V2.1 §9.0）必须原样写下这三句，避免现场以"我以为学生看不到"翻车。

### 4.4 文章：两步投屏（②）+ 分页实测（⑦）

**② 两步，我同意 Chief 的不对称，但理由要写对**：音乐"点即播"是因为上行内容是**曲名自动跟随**、一步可撤（点暂停）；文章的屏上内容是**滚动位置**，需要"定稿再上屏"，所以两步。不对称不是妥协，是两个内容物的性质不同。

```
article: idle → preview(在本机挑/翻) → presenting(已上屏) → idle(结束投屏→回 standby)
```

- 「开始投屏」= 把**当前这一屏**（含当前样式）原子下发；「结束投屏」= 回 `standby`（不是"等待控制台"，因为待机已有主题/黑屏两个形态）。
- 结束投屏**保留阅读位置**；再次投出从原位置继续。
- 单屏模式下这两个按钮进迷你控制条（`上一屏/下一屏` + `投出/结束`）。

**⑦ 分页（我的实现口径）**

| 项 | 规则 |
|----|------|
| 谁来算 | **渲染端**（display / 单屏页）。控制台的预览窗与投影物理尺寸不同，算不准也不该算 |
| 何时算 | `await document.fonts.ready` → `requestIdleCallback` 测量；**字体加载 3s 超时按 fallback 度量**（否则弱网永久白屏） |
| 怎么算 | ~~以「节 + 字符偏移」为原子，二分法找每页能容纳的最大偏移；产出 `pageMap = [{start:{verseSn,charOffset}, …}]`~~ **V2.1.6 作废**：改为**整章渲染行流 + 几何实测**（`lineY[]` / `verseLineIndex[]` / 页起点逐页递推 `pageStarts[]`），见 §4.8、§4.9 与正文 §7.5.1 |
| 变化即重排 | `ResizeObserver`（200ms debounce）+ 字号/字体/行高变更 → 重排 → **重发 pageMap** |
| 状态锚点 | **状态是 `anchor`，不是页码**：`{volumeId, chapterSn, verseSn, charOffset}`。重排后按 anchor 重新定位到"包含 anchor 的那一屏"，页码只用于显示「3/12」 |
| 「续」标记 | 放**页脚小字**（`::after` 或独立元素），**不得插入经文正文**——否则复制/朗读/校对会带脏字符，宗教场景尤其不能动原文。**V2.1.6 限定：只在 `unit=page` 出现**；`unit=section` 每屏都从节首开始，不需要「续」 |
| 禁止 | 显示端滚动（大屏无人操作）；`overflow:auto`；按字数/行数估算 |

控制页是笔记本上的缩略预览，显示端是 1080p 起的大屏，**同一段文字两边物理字号不可能一致**。能做到也必须做到的是：**内容一致**（第几章、第几屏、哪几行）。

### 4.8 V2.1.6：`unit=section` ＝视口按节步进（Jeremyzh 11:47 例子定死语义）

Jeremyzh 给的例子（诗篇 23；和合本 **6 节**，11:47 原话的「7 节」是笔误；每节折行后 2 行，视口 5 行）：

- 第 1 屏＝节 1 两行 + 节 2 两行 + 节 3 第 1 行
- 点「下一节」→ 节 2 两行 + 节 3 两行 + 节 4 第 1 行
- 再点 → 节 3 两行 + 节 4 两行 + 节 5 第 1 行

**结论：`section` 不是分页、不是章内分屏，是「视口按节步进」。** 屏高不变、起点对齐节首、底部允许露出半节、相邻屏必然重叠（本例 3 行）——**重叠是预期，不是 bug**。这句必须同时出现在文档与验收里，否则会被当缺陷报上来。

| 项 | 怎么办 |
|----|--------|
| 算法 | **V2.1.10 起：算术主线**——按字符宽度（全角 1／半角 0.5）切 `L[k]=ceil(节字数/charsPerLine)`、每行一个 `nowrap` 块 → `totalLines=ΣL`、`verseLineStart`=前缀和、`lineY[]` 由 `L×行高 + 段距` 算出 → **整节下移**装页得 `pageStarts[]`/`pageCount`/`viewLines`；`page` 走 `startLine=pageStarts[pageIndex]`、`section` 走 `startLine=verseLineStart[sectionIndex]`；`translateY(-lineY[startLine])`。DOM 实测只作校验（误差 >1px＝模型错，告警不得静默覆盖）。~~`N = floor(可用高/行高)`~~ V2.1.7 作废；~~逐页实测递推~~ V2.1.10 降为校验 |
| 定位 | 不切片文本：整章 DOM 常驻，外层 `overflow:hidden`，内层 `translateY(-lineY[startLine])`——**用像素，不做行号×行高换算**（换算引入 ±半行舍入，72px 下 63px 足够把节首顶掉半行） |
| 屏数 | `pageCount`＝**整章 page 屏数**（V2.1.10 起按算法算出）、`sectionCount`＝**整章节数**；两者**恒报、与 `unit` 无关**。`section` 模式只显示「节 3/6」、不显示「3/12」；不预存屏数组、不传每屏明细 |
| 越界 | 末节起不足一屏（实测容纳行数）→ 显示到章末、留空、**不回退起点**；`next` 到末节停住、提示「已到章末」、不跨章 |
| 「续」 | **只在 `unit=page`**；`section` 不需要，也不得因为「看起来接不上」补一个 |
| 「整章一屏」 | `pageCount>1` 时出现（它管「这一章要几屏」，与节数无关）；点击＝按步长 4 降 `fontSizePx` 到 `pageCount==1`；默认不动字号，实际值回报控制台 |
| 文案 | 「节」＝**经节 `verseSn`** → 按钮写「**上一节/下一节**」（V2.1.7 纠正 V2.1.6 的「节＝章」；跨章仍走 `article.navigate`） |

**原型裁行 bug（这一条是我写出来的，根因在测量方式）**：V2.1.5 的 `measurePages()` 建了一个**平行 ruler**，ruler 里的 `<p>` 写 `margin:0 0 .9em`、正文 CSS 写 `1.1em`，而 `getBoundingClientRect().height` **不含 margin**——累加里根本没有段距。后果是**默认 72px 下就裁行**：3 个两行节测得 756≤911 通过，实渲染 756+3×79.2＝993.6 → `.body{overflow:hidden}` 静默裁掉最后一行；7 个单行节测得 882、实渲染 1436。改法：**不要平行测量层**，整章先渲染、读每节 `offsetTop/offsetHeight`，按真实几何切页与定位节首。两份段距 CSS 也就不存在漂移。

**板书字号（Chief 第六条）**：`display.html` 原 `.cast .paper{font-size:min(calc(var(--cds-font-size)*.9), 6.5vh)}`——6.5vh 在 1080p＝70.2px，**字号 72px 以上对板书全部无效**，与「远处看清」直接冲突。改为同一 `fontSizePx` + 装不下按**步长 4** 自动降档 + **控制页显示实际生效值**；不做静默缩。与「整章一屏」同逻辑：**降字号必须被老师看见**。

**物理约束（写进正文 §5.2，给老师看）**：可用高 ≈911px，行高 = `fontSizePx×1.75` ⇒ 72px→5 行、96px→4 行、120px→**3 行**。**「上限 120px」与「一屏 5–6 行」不能同时满足**，这是算术。UI 要显式标出「首屏 N 行」，别让老师在课上发现。（**V2.1.10 更正**：上面 5/4/3 是填满优先口径，已作废；整节下移、`c=12` 下为 4/4/2，见 §4.12。）
### 4.9 V2.1.7：纠漂源、`pageMap` 分母、「节」的定义、行数更正

> 起因：开发 12:0x 提三问（经 Chief 转达）。三条中有两条是**我们会照着写出错东西**的旧口径，一条是数字错。另两条是我自查出来的。

**① 纠漂源方向反了（最严重，协议缺口）**

正文原写「每 5s 收到 `state.report.positionMs` 时算 `Δ`」。`state.report` 是 **display → 服务端的上行**，display 收不到自己的 report；即便自订阅也是拿自己刚发的值重锚，`Δ` 恒为 0、零纠偏，还会把上报延迟当漂移。

定稿：**新增下行 `player.sync {positionMs, durationMs}`**，由**音频宿主（控制页）每 5s 发**、服务端转发给 display；display 收到算 `Δ = (positionMs + delayMs) − pos(now)`，再走 80/300ms 三档。

- 为什么必须由音频宿主发：音频在控制页，只有它有真实 `currentTime`；服务端无音频，display 无 `<audio>`（V2.1 前提）。

  - **选 A：`player.sync` 随 V2.1 落地** → 按本节口径实现，验收 B6 两条可执行。

**② `pageCount` / `sectionCount` 的分母定死**

两个数**都恒报、与当前 `unit` 无关**：`pageCount`＝整章按 `page` 视口的屏数，`sectionCount`＝整章节数。`unit` 只决定**步进方式**与**显示哪一个**（`page` 显示「3/12」、`section` 显示「节 3/6」）。切 `unit` 不重发、页码不跳数，与 D-I「页码只用于显示」一致。

**③ 「节」＝经节（`verseSn`），不是章**

**④ 一屏行数更正（120px）**

| `fontSizePx` | 行高 | 首屏（整节下移、诗篇 23、`c=12`） | 全章屏数 |
|---|---|---|---|
| 72（默认） | 126px | **4 行**（583.2px；加节 3 需 914.4px 超） | 3 |

**⑥ 页容量不能是 `N = floor(可用高/行高)`（开发实测 + 原型都撞了）**

每节自带段距（约 0.63 行），真实容量永远小于纯行数：1080p、72px 时公式给 7 行、真实 5 行。按 `pageIndex×N` 定位，页边界会落在行中间 → `overflow:hidden` 下表现为「最后一行被切掉」且不标「续」，最坏情况下每屏都少一行、要翻到第 8 屏才看完整章。

**⑦ 顺带修**：「整章一屏」的出现条件由 `sectionCount>1` 改为 `pageCount>1`（它管的是「这一章需要几屏」，与节数无关）。

## 4.10 `player.sync` 定稿与原型复测回填（V2.1.8）

**① 字段定稿**：`player.sync {trackId, seq, positionMs, isPlaying}`，**删 `durationMs`**——display 只画歌词、不画进度条（进度条在控制页），时长对显示端没有使用点。

| 字段 | 谁用 | 为什么必须有 |
|---|---|---|
| `trackId` | display 丢弃旧曲 sync | 切歌瞬间若收到上一曲的 `positionMs`，歌词会被拉回到上一首的位置 |
| `seq` | display 只接受 `seq > lastSeq` | 重连后 Broker 可能重放旧包；拿 5 秒前的值重锚等于制造一次假漂移 |
| `positionMs` | `Δ = positionMs − pos(now)` | 唯一的位置来源 |
| `isPlaying` | 决定是否继续推进插值 | 暂停期间若仍推进，歌词会一路爬过整首 |

**② Δ 的算式改口径**：`Δ = positionMs − pos(now)`，**`delayMs` 不进 Δ、也不进 `base`**。
- 原写法把控制页测得的半程 `delayMs` 加进 `base` 与 `Δ`。它量的是「控制页→服务端」，要补的却是「控制页→显示端」**整段**——补一半留一半，且 `base` 与 `Δ` 用了不同口径，两个方向会互相抵消。
- 这段系统滞后（约 20–80ms）本来就落在 80ms 死区内；再用一个带估计噪声的常数去「精细补」，只会把 `Δ` 的基线推偏。§13 的 <120ms 预算覆盖它。
- `delayMs` 的测量代码可留，**只作 UI 诊断**（「网络较慢」提示）；review 口径：`rg -n 'delayMs' src/display/player/` 只允许命中诊断分支。

**③ 发送时机**：每 5s 一条；`connack` 之后、`visibilitychange → visible`、`presence online` 各**补一条**。三种「刚回来」的状态最容易带着旧值，只靠 5s 节拍要多等最多 5 秒——而这几秒正是显示端刚重连、最需要对齐的时候。

**④ 复测回填（原型实测，不是估；V2.1.10 起行数改由 `charsPerLine` 切行决定，这组自然折行的数只作历史记录）**：`.body.clientHeight = 580`、72px（行高 126）下诗篇 23 为 **14 行**（`verseLineIndex = 0/2/4/6/8/11`）、`pageStarts = 0/3/6/9/12`、**逐屏 3/3/3/3/2、共 5 屏**；96px → 6 屏；120px → 10 屏（末屏 1 行）。旧文「每屏 4 行」是错记：5×4=20 与 14 行自相矛盾。**V2.1.12 起作废**：见 §4.12（旧文按填满优先，与整节下移冲突）。

**⑤ 未采**：`ceiling(totalLines/N)` 与按行号×行高定位（见 §4.9 ⑥）；每屏明细表上行（见 §4.9 ③）。

**零 schema 变更**：`player.sync` 是消息、不是表；`pageMap` 仍不落库。

## 4.11 触屏 / 手机控制页与行距可控（V2.1.9）

**来源**：Jeremyzh 2026-11-18 12:13 四问，「控制端可以是手机」+「文章行数要可控，所以行间距人为选择」。

### ① 控制端可以是手机（P1，不改协议）

- **前提不变**：声音只从接了场地音响的那台电脑出（D-A′）。手机控制页**本身不放声**，音乐面板保持置灰，UI 必须写明原因。
- **触屏不能用手势发送**：双击＝浏览器缩放/选词，长按＝选词，两者与「双击发送」直接冲突。取**固定「发送」按钮**（拇指区、≥44px、`pointer:coarse` 下占满一行），而不是长按 600ms 手势——板书高频、发错内容直接上大屏，显式按钮误触代价更低。
- **双击保留但只给非触屏**：`dblclick` 绑定包在 `!isCoarse()` 分支里，桌面上行为不变（含 `preventDefault` + 选区收成光标）。
- **布局**：`(pointer:coarse),(max-width:900px)` 下单列、触控目标 ≥44px、发送按钮 ≥52px 高；`/#/console/player`、`/#/console/article` 同口径，不沿用桌面 grid。
- **手机上两个「顺序」问题（实测后加的，不是设计洁癖）**：① 当前场景卡**提到首屏**（`order:-1`）——否则老师要先滚过「今日预选」才够得着板书编辑区；② 发送条 **`position:sticky;bottom:0`** 并在手机上收成一行（仅「选择附件 + 投出」两个按钮，长提示在小屏不显示）——一行行写板书时按钮始终在拇指下，不必来回滚。
- **未在真机验证的部分（照实说）**：`pointer:coarse` 分支与触屏手势的**真机行为**由运维/开发在手机上验（本机只能用宽度 390 的窗口验布局，用 `matchMedia` 的布尔值验分支）；验收里触屏三条按真机写。

### ② 行距＝行数的控制手段（不需要新协议字段）

## 4.12 每行字数 `charsPerLine` 与算术分页（V2.1.10）

**来源**：Jeremyzh 2026-11-18 12:22 ——「每一行展示的文字和字符个数也可以控制」「你可以计算出这一篇文章总共有多少行，然后他的每一节的标识，其实它原文就是一节一行这样提供的」。

### ① 三个控制项 + 三个派生值

| 类 | 名字 | 量程 / 含义 |
|---|---|---|
| 控制 | `fontSizePx` | 24–120、步长 4、默认 72（已有）→ **V2.1.11 改：24–160，默认按屏高派生**，见 §4.13 |
| 控制 | `lineHeight` | 1.2–2.2、步长 0.05、默认 1.75（已有，V2.1.9 提到场景常驻） |
| 控制 | **`charsPerLine`** | **6–40、步长 1、默认 12（V2.1.10 版）**；全角计 1、半角计 0.5 → **V2.1.11 改：默认 `"auto"`、手动 6–24**，见 §4.13 |
| 派生 | `totalLines` | 全篇行数 ＝ `Σ ceil(节字数 ÷ c)` |
| 派生 | `verseLineStart[k]` | 每节首行号 ＝ 上述数组的前缀和（`0/2/4/6/9/12`） |
| 派生 | `pageCount` | 屏数（整节贪心装页的序列长度） |

**默认 12 的依据**：它给出 15 行 3 屏、首屏 4 行，最接近 Jeremyzh 11:47 目测的「一屏 5 行」（15÷3＝5 是平均；逐屏其实 4/5/6）。若按自然折行（72px、1920 宽 ≈24 字/行），会变成每节 1 行、9 行 2 屏——那不是他举的那个。

### ② 硬约束：`charsPerLine × fontSizePx ≤ 可用宽`（联动 clamp）

1920 宽扣 5vw×2 → 可用 **1728px**：

| `fontSizePx` | 24 | 48 | **72** | 96 | 120 |
|---|---|---|---|---|---|
| `charsPerLine` 上限 | 72 | 36 | **24** | 18 | 14 |

- 控制台滑块 `max = min(40, floor(可用宽 ÷ fontSizePx))`，字号一变立刻降上限并把当前值 clamp 到新上限，旁边写「上限 18 字」——**不许静默改值**（老师得知道被改了）。
- `mqtt.md` V2.2.8 写的「6–24」是 **72px 这一档**的上限，不是总范围；总范围按 6–40，越界由 clamp 收。

### ③ 分页从「测量」改「算术主线」（DOM 实测降为校验）

自然折行不可算（中英数混排宽度不同、fallback 字体不同），因此：

1. 按字符宽度切行，`L[k]=ceil(节字数/c)`，每行一个 `white-space:nowrap` 块，**行数＝数组长度**；
2. `totalLines`/`verseLineStart`/`lineY` 全部由 `L`、行高、段距算出（段距恒 `1.1em`，`lineHeight` 不改它）；
3. 装页用**整节下移**（唯一规则），`pageCount`＝序列长度，`viewLines`＝**首屏**行数；
4. 渲染后用 `offsetTop/offsetHeight` 校验，误差 >1px 即模型错，**告警不得静默覆盖**。

（完整 6 步见 `前端设计-V2.1` §7.5.1。）

### ④ 算例（诗篇 23、72px/1.75/911；与开发 `mqtt.md` V2.2.8 §4.6.3 逐格一致）

| `c` | 8 | 10 | **12** | 14 | 16 | 24 |
|---|---|---|---|---|---|---|
| `totalLines` | 20 | 19 | **15** | 14 | 11 | 9 |
| `pageCount` | 5 | 4 | **3** | 3 | 3 | 2 |
| 首屏 | 5 | 5 | **4** | 4 | 5 | 5 |

这 12 个数字我用独立脚本（字符宽度模型 + 整节贪心）算过一遍，与开发 §4.6.3 完全相同——**两处独立实现得同一组数**，这才敢写进验收。

### ⑤ 与 V2.1.9 那两张表的冲突（已作废）

V2.1.6–2.1.9 写的「72px→5 行 / 96→4 / 120→3」「行距 1.2→7 行」都是**填满优先**（把自身不到一屏的节切开填满当屏）算出来的。`mqtt.md` V2.2.8 定死整节下移后，同参数结果为 **72→4 / 96→4 / 120→2**（`c=12`、行距 1.75）。两种规则对同一首诗篇 23（`c=8`）分别是 5 屏与 4 屏——**屏数不能随实现者变**，所以只留整节下移。

### ⑥ 数据前提（已核）

`migrations/0001_init_core.sql` L94–100 `verses(book_id, chapter_sn, verse_sn, verse_txt)` + UNIQUE，**一节一行**，正是「每一节的标识，原文就是一节一行」的落地；**零 schema 变更**。`charsPerLine` 只切视觉行，不动 `verses` 文本。

### ⑦ 已知缺口（照实说，不塞进 P0）

- **避头尾未做**：按宽度硬切，全角标点可能落在行首（`，`「。」开头）。P1 再加「标点悬挂/挤压」，验收**不判**这一条。
- **半角宽度是近似**：`Li 3:16` 里字母、数字、空格都按 0.5 算；等宽/比例字体差异不追。
- **列宽语义未定**（开发 §4.6.4 同款问题）：`c=12 × 72px = 864px` 只占 1728 的一半，撑满会留半屏空白。我的建议：块宽＝`c × fontSizePx` 居中，这样「每行 12 字」在视觉上成立；待 Jeremyzh 看一眼原型再定。

## 4.13 默认值改派生（方案 A 保留）+ 跨屏一致性（V2.1.11）

**来源**：Jeremyzh 2026-11-18 12:36 ——「保留方案 A……先固定一个比较自动的值，我的投屏界面可能是 1920×1080，也可能是 2K 或 4K，所以我都需要能根据当前字号的大小来调整每行显示多少个字。」

### ① 两个默认值都不是死数字

| 参数 | 默认 | 手动档 | 派生式 |
|---|---|---|---|
| `fontSizePx` | 按屏高派生 | 24–160 / 步长 4 | `round4(屏高 × 6.7%)` ⇒ 720p 48、1080p 72、1440p 96、2160p 144 |
| `charsPerLine` | `"auto"` | 6–24 / 步长 1 | `N = clamp(6, 24, floor(W ÷ fontSizePx))`，`W = .body.clientWidth` |

- **派生在显示端算**：服务端既不知道 `W` 也不知道 `F`，不得代算；`ack` 必须回带 `effective:{fontSizePx, lineHeight, charsPerLine}`（`auto` 回派生整数），否则控制台会以为请求生效了。
- **三档自洽**：1728/72＝24、2304/96＝24、3456/144＝24。
- **`fontSizePx` 上限 120 → 160**：2160×6.7%≈144.7→**144**（落在 4 的网格上）；120px 在 4K 上字高只占 5.56%（1080p 的 72px 是 7.11%），观感偏小。

### ② 上限 24 是**可读性**底线，不是技术限制

24px 字号下 `floor(1728/24)=72`、48px 时 36，屏上装得下——但**一行超过 24 个全角字，后排跟行会跳字**。所以：协议（`mqtt.md` V2.2.10）字段容错接受 6–40 整型，25–40 到达显示端一律收紧到 `min(24, floor(W÷F))` 并回带 `effective`；**产品 UI 量程就是 6–24**。这条写进正文是为了让下一轮不能以「装得下」为由放开成 72。

### ③ 跨屏一致性（A 方案唯一可证伪的断言）

诗篇 23（16/21/21/25/32/32＝147 字、整节下移、行距 1.75、段距 1.1em）：

| 屏 | `F` | `W` | `H` | `auto c` | 每节行数 | 行数 | 屏数 | 逐屏 |
|---|---|---|---|---|---|---|---|---|
| 720p | 48 | 1152 | 608 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |
| 1080p | 72 | 1728 | 911 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |
| 2K | 96 | 2304 | 1296 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |
| 4K | 144 | 3456 | 1944 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |

**边界（不要写过头）**：`auto` 保证「每行字数与屏宽同比例」，因此**行数序列**一致；**屏数**还取决于 `H÷F`，而 `H` 含不随屏缩放的页眉页脚。四档 `H÷F` **按原型实测（V2.1.12）＝ 12.23 / 12.53 / 12.68 / 12.83**，全在 `12.05 ≤ H÷F < 16.65` 内。（原写 12.67/12.65/**13.5**/13.5 中的 13.5 是「屏高×0.9、不减页眉」的算法，**作废**，见 §4.14 ②。）**反例**：页眉页脚绝对高变大 → 1080p 的 `H÷F` 跌破 12.05（`H` < 867.6）→ 1080p 变 3/4/2、4K 仍 2 屏 ⇒ 分叉。验收只钉这四组输入。

### ④ 4K 电视的坑

大量 4K 电视以 **DPR=2 报 1920×1080 CSS px**，行为与 1080p 完全一致；**一律按 CSS px viewport 判**，只有真报 3840 宽才用 144px。

### ⑤ 连带订正（V2.1.10 的默认口径作废）

- `前端设计` §7.5.1 算例表：`12（默认）`→**手动档**；`24`→**现默认**（`auto` 在 1080p 的派生值）。
- 行距示例按 `auto` 重算：72px（`c=24`）1.2/1.75/2.2 → 首屏 **5/5/3** 行（2/2/3 屏）；锁 `c=12` 时仍是 6/4/4（3/3/4 屏）。
- 验收参考表拆成 **默认 `auto`** 与 **锁定 `c=12`** 两组，fixture 基准改为默认档：9 行 / 2 屏 / 5/4 / `viewLines=5`。
- 原型：`display.html` / `screen.html` 的 `pageMap` 曾把 `charsPerLine` 塞进载荷（8 键）——**已从 `pageMap` 移除**，生效值改走单独的 `styleAck`（对齐 `mqtt.md` V2.2.10「恒 7 字段」）。

## 4.14 V2.1.12：实测口径三修（`W` 的取法 / `H` 的实测值 / 1640 宽反例）

**① `W` 不能取 `#content.clientWidth`。** 它含 5vw 左右 padding：1280 屏读到 1280，真可用只有 1152 → `c` 算成 24，行宽 24×52=1248 > 1152，`overflow:hidden` 下行尾静默裁掉 **131px**（实测）。定稿：`W = .body.clientWidth − padding`；渲染期 `.body` 未插入时用 `0.9 × innerWidth`。控制台的「每行上限」按显示端回报的 `layoutMetrics.availW` 算。

**② `H` 用实测值，`13.5` 作废。** `.body.clientHeight` 实测 720p **587** / 1080p **902** / 1440p **1217** / 4K **1847**，`H÷F` ＝ 12.23 / 12.53 / 12.68 / 12.83。`mqtt.md` V2.2.10 写的「2K/4K 为 13.5」是「屏高×0.9、不减页眉」的算法——按 13.5 反推页眉高度会得负数。协议侧 §4.6.3 的 608/911/1296/1944 是另一套（页眉页脚按 61px 扣），**两套 H 都判 9 行 2 屏 5/4**，所以结论不变，但数字必须各写各的，不能互推。

**③ 1640×1080 是必须留着的反例。** `floor(1476/72)=20` → 每节第二行多切一刀，11 行 3 屏 5/4/2。四档（720p/1080p/1440p/4K）得 24 字/行，是因为 `W÷F` 恰好整除到 24 以上；**「24 字/行」不是常数**，验收不得把 1640 也写成 9 行 2 屏。

**④ 新缺陷备案（P1）**：节号 `.sn` 占首行宽度 → 首行行尾被裁，实测 27px（1280×800）/49px（1920×1080）/98px（4K）。修法① 悬挂进 5vw 留白（改裁剪结构）、② 首行少 1 字（改行数算术），都会动摇四档表，**未定，先备案不修**。

**⑤ 1280×800 定档**：`clientWidth=1152`、`clientHeight=657`、派生 52px、`c=22` → 9 行、2 屏 5/4。
