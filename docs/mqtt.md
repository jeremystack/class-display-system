# Class Display System MQTT 通信协议

## 📋 文档信息

- **版本**: V2.2.20（V2.2 基线 + V2.2.1…V2.2.20 订正，见 §9 变更记录）
- **更新日期**: 2026-11-18
- **Broker**: EMQX Cloud
- **传输**: MQTT 5.0 over WebSocket (WSS)
- **消息格式**: JSON (UTF-8)

> 口径说明：本协议承载**音乐播放控制**、**文章阅读导航**、**投屏**、**设备状态**。文章导航只下发"显示哪一章、滚动到哪一节"，**不存在朗读、语速、音量类指令**。

## 1. 连接

### 1.1 参数
```
URL        : wss://{EMQX_URL}:{EMQX_WSS_PORT}/mqtt
ClientID   : cds-{role}-{deviceId}         例如 cds-display-dev_001
Username   : {EMQX_USERNAME}
Password   : {EMQX_PASSWORD}         // 共享口令（运维 R-14：现网认证后端只有一组账密）
// 注意：设备身份**不**走 MQTT 密码。应用层用 dev/sig（V2.3），key = devices.token_hash
KeepAlive  : 30s
CleanStart : false        // 依赖 session 持久化补投
```
- **必须走 WebSocket 传输**：`transport=websockets`、`path=/mqtt`（MQTT 5 over WSS）。2026-11-18 12:27 实测：该端口**不接受裸 MQTT/TCP**——裸 TCP 能建立连接、`CONNECT` 也能发出，但**永远收不到 `CONNACK`**（且不报 TLS/WS 错）。会被误判成「认证失败」而去查口令，排查方向反了。
- CONNACK 返回的 broker 能力（实测）：`RetainAvailable=1`、`MaximumPacketSize=1048576`、`TopicAliasMaximum=10`、`ReceiveMaximum=32`、`WildcardSubscriptionAvailable=1`。1 MiB 上限意味着「整张分页表」塞得进包体——但那不是理由，见 §4.4 只报摘要。

### 1.2 在线状态（LWT）
```
Topic   : cds/v1/{deviceCode}/presence
Payload : {"online":false,"ts":1763350000000}
Retain  : true
QoS     : 1
```

### 1.3 ACL 约束
| 角色 | 可发布 | 可订阅 |
|------|--------|--------|
| 显示端 | `cds/v1/{自己的 deviceCode}/state`、`.../ack`、`.../presence` | `cds/v1/{自己的 deviceCode}/cmd` |
| 服务端 | `.../cmd` | `.../state`、`.../ack`、`.../presence` |

**上表是目标态，现网不是这样。** 2026-11-18 12:28 实测（MQTT 5 over WSS，共享口令）：
- 订阅：`#` → SUBACK 135、`$SYS/#` → 135；`cds/#` → 授予 QoS 0、`cds/v1/+/cmd|state|ack|presence` → 授予 QoS 1、`foo/#` → 授予 QoS 0。⇒ 只拦了**根通配** `#` 与 `$SYS/#`，任意**具名前缀**的通配全放行（换个子树照样看全站）。
- 发布：`cds/v1/{任意 deviceCode}/cmd|state|ack|presence` 及任意 `cds/` 子主题 → **PUBACK 0 全部成功**，自订阅回环能收到。

⇒ 现网 ACL 近似「全放行」，**不构成任何隔离**。共享口令持有者可以读全站、向任意屏发指令、伪造 retained 状态（详见 §7）。实现时**不得**依赖本表做隔离；切到「HTTP authn → Worker + 按 Topic ACL」之后本表才成立。

## 2. Topic 设计

```
cds/v1/{deviceCode}/cmd       服务端 → 显示端   指令   QoS1, retain=false
cds/v1/{deviceCode}/ack       显示端 → 服务端   回执   QoS1, retain=false
cds/v1/{deviceCode}/state     显示端 → 服务端   状态   QoS1, retain=true
cds/v1/{deviceCode}/presence  显示端 → 服务端   上下线 QoS1, retain=true
```

## 3. 消息包络

```json
{
  "v": 1,
  "msgId": "m-8f2c1a7b",
  "ts": 1763350000000,
  "type": "player.play",
  "payload": { }
}
```
- `msgId`：服务端生成，全局唯一；显示端在 5 分钟内按 `msgId` 去重（幂等）
- `ts`：发送方时间戳（毫秒），显示端与本地时钟偏差 > 5s 时以服务端为准
- `type`：`域.动作`，见 §4

## 4. 指令与状态

### 4.1 音乐播放

#### player.play
```json
{
  "v": 1, "msgId": "m-01", "ts": 1763350000000, "type": "player.play",
  "payload": {
    "musicId": "f3f9f5b21b630e07d99f01c5b7778aa5",
    "audioUrl": "https://xxx.xxx.top/assets/xxx.mp3",
    "track": "main",
    "lrc": "[00:11.85]宇宙广阔无垠\r\n",
    "coverUrl": "https://xxx.xxx.top/assets/xxx.jpg",
    "positionMs": 0,
    "volume": 50
  }
}
```

- 产品稿 §10.6 的 `delayMs` / `durationMs` 本协议**不定义**（理由见 §4.1「时基约定」）；显示端对未定义字段一律忽略

#### player.pause / player.resume / player.stop
```json
{ "type": "player.pause", "payload": { "positionMs": 42500 } }
```
停止时 `payload` 可带 `{ "fadeOutMs": 300 }`。

#### player.seek
```json
{ "type": "player.seek", "payload": { "positionMs": 61200 } }
```

#### player.volume
```json
{ "type": "player.volume", "payload": { "volume": 65 } }
```

#### player.track
```json
{ "type": "player.track", "payload": { "track": "accompaniment" } }
```

#### player.sync（服务端 → 显示端）
音频宿主（＝控制页）每 5s 上报一次真实播放位置，服务端**原样转发**给该教室的显示端；这是显示端**唯一**的时基校正来源（V2.2.5 起生效，随 V2.1 落地，不再等 V2.3）。
```json
{
  "v": 1, "msgId": "m-77", "ts": 1763350005000, "type": "player.sync",
  "payload": {
    "trackId": "f3f9f5b21b630e07d99f01c5b7778aa5",
    "seq": 42,
    "positionMs": 187340,
    "isPlaying": true
  }
}
```
- `trackId`：当前曲目（＝`player.play.musicId`）。显示端发现 `trackId` 变化时按**新曲目**处理，不得沿用旧 `t0`
- `seq`：控制页**单调递增**（从 1 起）。显示端丢弃 `seq ≤ 已处理值` 的包（防乱序/重放）；`seq` 变小＝控制页重载，显示端按新序列接受、并等下一帧锚定
- `positionMs`：控制页**发出时**音频元素的实际位置（`audio.currentTime * 1000`，整数毫秒）
- `isPlaying`：发出时的播放状态。`false` 时显示端**停止本地推进但不重锚**（画面状态仍由 `player.pause` / `player.play` 决定，不由本消息翻转场景）
- QoS1、`retain=false`；显示端**不得**据此持久化，**不得**回写 `playback_state`（`playback_state` 只由控制页的播放控制写入）
- 发送时机：每 5s 一条；另在 `connack` 成功后、`visibilitychange → visible`、`presence online` 各**补一条**（保证重连后 5s 内不会拿过期锚点跑）
- **`article` / `cast` 场景下到达的 `player.sync` 一律忽略**：这两个场景禁音乐（见本节末「投屏与音乐的关系」），此时不得据此起播、不得推进歌词、不得翻转场景状态。控制页切场景前已 `player.pause`，正常不会出现；这条防的是「迟到的 sync 把文章场景点亮」。
- **本地推进必须有上限（手机控制端必需）**：显示端连续 **15s** 未收到任何含时基的下行帧（`player.play|pause|resume|seek|sync`）→ **冻结位置**，并在 `state.report` 的 `nowPlaying` 里带可选 `stale: true`，直到下一帧到达。理由：音频宿主是**控制页**，控制页可能是手机——`visibilitychange→hidden` 立即暂停、回前台不自动续播（`前端设计-V2.1` §9）；手机后台挂起/4G↔Wi-Fi 切换时下行会断几分钟，无限外推会让歌词持续跑到音频前面（现场症状是「歌词越跑越远」，且回来时 `|Δ|>300` 直接跳，看起来像分页/时基 bug）。15s = 「5s 一帧 × 3 次未到」，可调但**必须有界**。`stale` 为 V2.2.7 新增的**可选**字段（前向兼容：未定义字段忽略），仅供控制台显示「显示端已冻结」。
- **无 `atMs` / `startedAtEpochMs`**：显示端不做任何跨设备时钟换算（理由见下方「时基约定」）
- 产品稿 `前端设计-V2.1` §10.6 写作 `{positionMs, durationMs}`；本协议**不定义 `durationMs`**——显示端不画进度条、也不按总时长做任何计算。未定义字段一律**忽略**（见 §3 前向兼容），两侧并存不会出错

**时基约定（V2.2.5 定稿，全协议唯一）**
- 显示端只用**本地单调时钟**：`t0 = performance.now()`，`pos(t) = base + (performance.now() − t0)`。**不得**用 `Date.now()` 做插值——D-1 的盒子/电视棒普遍无 NTP，墙钟跳变会让歌词整段跳（`前端设计-V2.1` §10.6 同一禁令）
- 收到 `player.sync` 时：`Δ = positionMs − pos(now)`，按 **80 / 300 ms 三档**处理——`|Δ| < 80` 忽略；`80 ≤ |Δ| ≤ 300` 慢追（每帧靠 10%、单帧 ≤5ms）；`|Δ| > 300` 直接跳（`base = positionMs; t0 = now()`）。三档的策略口径唯一来源是 `前端设计-V2.1` §10.6，本协议不复述
- **纠漂源只能是本消息（下行）**。`state.report` 是显示端→服务端的**上行**，display 收不到自己的 report；即便自订阅也是拿自己刚发的值重锚（`Δ` 恒 0、零纠偏），还会把上报延迟当漂移
- **残余误差 ＝「控制页 → 服务端」＋「服务端 → 显示端」两段单程之和 `R`**（音频宿主是控制页、不是服务端，**别只算后一段**；典型 40–100ms）。**稳态滞后上界就是 `R`**：`positionMs` 是控制页**发出时**的位置，显示端收到时音频已前进 `R`，故 `Δ = positionMs − pos(now) ≈ −(R + e)`（`e` ＝ 显示端相对真实音频位置的偏差），`Δ → 0` 收敛到 `e = −R`，即显示端**稳定落后 `R`**——既不是「落后一个单程」，也不收敛到 0。**80ms 死区只抑制小于半帧的抖动修正、不吸收残余**：`R ≤ 80` 时完全不纠（滞后＝`R`）；`80 < R ≤ 300` 时慢追停在死区边界，滞后落在 `[R−80, R]` 内（每轮 5s 回到上界）。这是刻意取舍：不引入 `delayMs` 一类**估计量**去补偿（两段单程都不是常数，估计偏差还会把歌词推到音频之前）
- **预算判定用 `R`，不用单程（V2.2.11 订正）**：`前端设计-V2.1` §13 的「跨文档歌词误差 <120ms」是**总预算**，故**装机合格线＝`R ≤ 100ms`**（留 20ms 余量）、**`R > 120ms` 判不可达**、`R` 落在 100–120ms 属**临界**须现场复测后书面确认。⚠️ 早前写的「单程 ≤80ms 时 <120ms 才成立」**作废**：两段各 80ms ⇒ `R = 160ms`，已超预算；**单程 80ms 只是纠漂阈值（死区半宽带）**，不是预算线。装机预检必须**逐教室实测 `R`**（控制页触发 `seek` 后比对显示端落点时间差，或两端各记 `performance.now()` 相减），留档备查，不得事后当 bug 查。例：4G 备份链路单程 150ms ⇒ `R ≈ 300ms`，<120ms 不可达，此时只能按「300ms 跳档」纠偏，不得承诺 §13 指标
- 5s 纠漂只吸收**运行期漂移**与**短时抖动**；跳档（seek、切曲）由 `seq` 递增 + `positionMs` 突变识别，不额外下发「seek 事件」

### 4.2 文章阅读导航（无播放控制）

#### article.navigate
下发"看哪一章、停在哪一节"：
```json
{
  "v": 1, "msgId": "m-11", "ts": 1763350000000, "type": "article.navigate",
  "payload": {
    "volumeId": 18,
    "volumeName": "约伯记",
    "chapterSn": 3,
    "anchorVerseSn": 12,
    "displayMode": "scroll",
    "fontSizePx": 72
  }
}
```
- `displayMode`: `scroll` | `page`（页面滚动/翻页，人工逐屏推进）
- `fontSizePx`: 可选，整型 **24–160、步长 4**（V2.2.12 上限由 120 提到 160，见 §4.6）；缺省时沿用本机已生效字号（来自 `display.style`，**含其派生默认值**，见 §4.6 字段表）。显示端**直写** `--cds-font-size`（px，不经 rem 乘法）；越界 `clamp(24,160)`，非 4 的倍数向下取整。
- `fontScale`: **已作废（V2.2.13）**——收到一律**忽略**并记 warn，改用 `fontSizePx`。历史：V2.2.2 曾把它重定义为 `fontSizePx` 的乘数（`clamp(24,200,fontSizePx × fontScale)`），V2.0 的「18px 基准 × fontScale」更早已作废；两条**都不要再实现**（作乘数时 `72×1.15=82.8` 越出步长网格；与 `fontSizePx` 并存还会乘两次）。
- **无** `speed`、`volume`、`autoPlay` 字段；服务端收到此类字段一律忽略并记 warn 日志

#### article.scroll
控制端手动翻屏 / 翻节（点击"下一屏"/"下一节"时）：
```json
{ "type": "article.scroll", "payload": { "direction": "next", "unit": "page", "steps": 1 } }
```
- `direction`: `next` | `prev`（`down`/`up` **已作废**（V2.2.1）——语义是"文档流向前/向后"，与屏内滚动方向解耦）
- `unit`: `page` | `section`，缺省 `page`。`page` = 按渲染实测的一屏；`section` = 一个"节"（章内分节；超长节内部再按屏分，分屏处标"续"）
- `steps`: 正整数，缺省 1
- **`lines` 字段删除（V2.2.1 起）**：分页以渲染实测（`document.fonts.ready` + 二分 + `pageMap`）为准，"按行数翻页"在 V2.1 起无意义；`验收清单-V2.1` 有 `rg -i 'lines' src/` 断言，任何 `article.*` 出现 `lines` 即判失败
- 越过章末 → **停末屏**并提示"已到章末"，不跨章（跨章走 `article.navigate`：`chapterSn±1`、锚点归章首）
- 不新增"上一节/下一节"指令：`unit=section` + `direction` 已覆盖；`article.navigate` 只负责"跳到某章某节"

**行为定义（V2.2.3 补：此前只有字段、没有行为，照字面会做成"翻页"）**

- **`unit=page`**：起点前进 `steps` 屏。一屏的边界由显示端**渲染实测**得出（须等 `document.fonts.ready`；段距计入），**不是**"行数 × 步长"，也**不是** `floor(可用高度 ÷ 行高)`。至于是"顺序填充"还是"整章连续行流 + 像素偏移"，属显示端实现选择，协议不约束；协议只要求两条：切点落在**整行**（不得横切行盒）、`pageCount` 来自**实测页序列**而不是算出来的。
- **`unit=section`**：起点 = 目标节的**首字符** `{verseSn, charOffset: 0}`，显示端从该字符起重新填充视口到满（到章末自然截断）；`steps` = 前进几节，缺省 1。
  **相邻屏允许重叠**：节边界一般不对齐屏边界，第 N 屏底部露出的半节会同时出现在第 N+1 屏顶部（诗篇 23 例：视口 5 行、每节 2 行 → 屏1 = 节1+节2+节3首行；下一节 → 节2+节3+节4首行；再下一节 → 节3+节4+节5首行）。这是预期行为，不是重复渲染，也不是 bug（例中「视口 5 行」只用于演示重叠逻辑，不是任何默认参数下的容量：1080p/72px、`charsPerLine=12` 时首屏是 **4 行**；默认 `"auto"` 在 1080p 派生 24 字/行，首屏 **5 行**，见 §4.6.3——真实容量以 §4.6.1 的算法结果为准，DOM 实测只作校验）。
- **某节自身超过一屏时，在该节内部继续分屏**（页脚标"续"，下屏从切割点续写，**正文不插任何字符**）：否则该节尾部永远不可见。大字号下必现——1080p 可用高度约 902px（实测；`#content` 上下 5vh + 页眉 + 页脚），行高 1.75 ⇒ `fontSizePx=120` 时一个 4 行节 = 972px 已装不下，必须切开。
- **`steps` 不跨章**：`page` 模式越过章末停末屏；`section` 模式最后一节即终点。两种情况都提示"已到章末"，跨章一律走 `article.navigate`。
- **页容量不是单值、也不上报整张表；但自 V2.2.8 起页容量是「算出来的」**：`N` **不是排版常数**——`.body p` 每节有 1.1em 段距（约 `0.63` 行）。同样 902px、`fontSizePx=72` 时，按 §4.6 的**整节下移**规则：单行节能装 **4 节 4 行**，两行节能装 **2 节 4 行**；而 `floor(902 ÷ (1.75 × 72))` = **7**，高估 **75%**。
- **（V2.2.8 订正 V2.2.6 的一处口径）**「两行节能装 5 行（2 节 + 第 3 节首行）」建立在一个**未被写下来的前提**上：允许把「自身不到一屏」的节切开以填满当屏（填满优先）。该前提与本节「某节自身超过一屏时才在节内继续分屏」直接冲突，且会让同一文档的屏数随实现者不同（诗篇 23、`charsPerLine=8`、72px：整节下移 **5 屏**、填满优先 **4 屏**）。**V2.2.8 定死整节下移**（§4.6 第 4 条），5 行口径作废。
- **行号不进协议，但行数已可算**：`totalLines` 与每节首行行号数组**仍不进协议、不上报**；V2.2.8 起行数由字符宽度模型（全角 1／半角 0.5）＋`charsPerLine` 决定，**不再随字体 fallback 变**（例外：溢出兜底重切，见 §4.6）。控制台仍只能读 `pageMap` 的 `pageCount`/`viewLines`，不得自算。
- **`viewLines` 进协议，但只作单个整数旁注**（V2.2.6）：语义＝**首屏容纳的完整行数**（`pageStarts[0]` 那一屏），供控制台旁注「首屏 N 行」，**不是每屏行数、也不是平均行数**。后续屏可能更少（多页时序列可能形如 3/3/3/3/2），故文案必须写「首屏」；禁止据此推算 `pageCount`，也禁止控制台自行用公式算。它与「不传每屏数组」不冲突——一个整数不是表。
- **（V2.2.4）屏容量不得用公式算**：`N = floor(可用高度 ÷ 行高)` 只在「无段距、无换行差异」时成立，**不得**当作页容量，更不得用它推屏数（`ceil(总行数 ÷ N)`）。段距 `1.1em` 使每个节额外占 `0.63` 行：1080p 可用高约 902px、行高 126px（`fontSizePx=72`）时公式给 `N=7`，而含段距的真实容量是 **4–5 行**（随节结构变）——屏数必然少算 30% 以上，且每屏底边落在行中，被 `overflow:hidden` 横切（静默、无标记）。页起点必须**逐页实测递推**：从当前页首行起，累加 `offsetTop` 差（含段距）直到再加一行就超过可用高度为止，取上一行为本页末行；`pageCount` = 该序列长度，不是算出来的。
- **（V2.2.4；V2.2.6 订正量级）节首定位不得换算行号**：`verseLineIndex[k] = round(offsetTop ÷ 行高)` 把**含段距的偏移**按行高折算。误差**不累积**：每节按自己的绝对 `offsetTop` 独立取整，残差封顶 ±0.5 行（72px 即 ±63px、120px 即 ±105px）。早前「第 10 节偏 6 行 ≈790px」的说法**作废**——那是把行号当成不含段距的行数累加去比，算法本身不成立；任何人不得据它做补偿。但 ±63px 已够把节首顶掉半行，故仍**不得**用它定位。真正会累积的是 `unit=page` 的 `pageIndex × N`：`N` 与真屏容量不等，每页偏 `0.63` 行、第 k 页偏 `k × 0.63` 行——已由**逐页实测递推**取代。正确做法：`translateY(-offsetTop(sectionEl))`，**只做像素偏移、不做行号换算**；行号如仅用于展示，可由实测页序列反查，不得参与定位。

```json

  "payload": { "castId": "cast_02", "contentType": "pdf",
```

- 预签名硬约束（D-03）：bucket 私有、URL 只读、有效期 ≤10 分钟、按 `deviceCode` 授权；显示端**不得转存**到公共位置或长期缓存

#### 投屏与音乐的关系（D-04 已废弃；按 V2.1.2 定稿，2026-11-18）
- `cast.start` / `cast.end` **不带任何 `player.*` 副作用**：服务端不隐式暂停、不改音量、不动播放位置（**此句不变，仍是硬约束**）
- **`cast` 场景下不得有音乐**（Jeremyzh「板书时不要放配乐」）。禁在**编排层**，不在 `cast.*` 里加副作用：控制服务先下发 `player.pause` → 收到 `ack{ok:true}` → 再下发 `cast.start`；**`ack` 1.5s 未到仍切画面**（丢包不应把老师卡在音乐页），控制台标「音乐未确认停止」并给停止键。D-A′ 之后音频在**控制台本地**、`audio.pause()` 同步生效，不依赖该 ack，故不会出现"画面已投、音乐还在响"
- 自动暂停必须给操作者一行**非阻塞提示**（「板书期间不播放音乐」），否则老师会当成故障、反复点播放再被停
- `cast.end` **不自动续播**：落回 `standby`（`standby` 允许背景音乐），等操作者点"继续"
- 兜底：`cast`（及 `article`，见 `前端设计-V2.1` §9.2）场景下收到 `player.play` / `player.resume` → `ack { ok:false, code:4009 }`
- 前提修正：V2.1 起 `display` **无 `<audio>`、永不发声**，声音由控制页播放后经现场音响（HDMI/线路输出/蓝牙）到达大屏。故旧句"显示端在 `cast` 图层上继续渲染音频播放"不成立，已删；"投屏期间音乐继续播放"也不再是协议行为，而是**被业务禁止**

#### state.report（显示端主动上报，retain=true）
```json
{
  "v": 1, "msgId": "d-07", "ts": 1763350000000, "type": "state.report",
  "payload": {
    "online": true,
    "nowPlaying": { "type": "music", "id": "f3f9...", "positionMs": 42500, "isPlaying": true, "volume": 50 },
    "viewing": { "volumeId": 18, "chapterSn": 3, "anchorVerseSn": 12 },
    "pageMap": { "anchor": { "verseSn": 12, "charOffset": 0 }, "pageIndex": 2, "pageCount": 12,
                 "unit": "page", "sectionIndex": 3, "sectionCount": 6, "viewLines": 5 },
    "casting": false,
    "layout": { "availW": 1728, "availH": 902, "fontSizePx": 72, "lineHeight": 1.75, "charsPerLine": 24 },
    "appVersion": "0.1.0"
  }
}
```
- 音乐每 5s 或状态变化时上报；文章阅读只在章节切换或位置变化时上报（不做进度同步）
- **`playback_state` 的写入路径唯一（V2.2.7 订正）**：只有控制页的 REST 播放控制（`play`/`pause`/`seek`/`stop`）可以写；`state.report` **只用于展示与对账**，服务端**不得**用它的 `nowPlaying` 回写 `playback_state`。原文「分流写入」与 §4.1「`playback_state` 只由控制页的播放控制写入」自相矛盾；且现网共享口令下任意第三方都能向该 topic 发 **retained** report（§7 实测），回写等于把全站播放状态交出去。阅读位置（`viewing`）照旧不入 `playback_state`，见 API 3.5。
- **过期上报必须丢弃（手机端必需）**：控制端可能是手机，4G/Wi-Fi 切换会让重连后重发的 `state.report`（§6-2 要求）乱序到达。服务端按 `deviceId` 维护「已处理的最大 `ts`」，**丢弃 `ts` 小于该值的 report**；重复 `msgId` 直接忽略。否则旧位置/旧页号会覆盖新值——典型症状是「手机切回 Wi-Fi 后页码/播放位置倒退几秒」。
- **`layout`：显示端实测几何 + 生效三参（V2.2.15 新增）**：`{availW, availH, fontSizePx, lineHeight, charsPerLine}`，五项必须取**同一帧**的实测值（`availW`/`availH` ＝ `#content .article .body` 的 `clientWidth`/`clientHeight`，`fontSizePx` 取 `getComputedStyle` 的 px，`charsPerLine` 取 `auto` 派生后的**整数**）。**单屏形态（D-3，显控一体）与多场景显示端同口径，同样必须上报**（V2.2.20 补：原型 `screen.html` 此前只发 `pageMap`，控制台在 D-3 下拿不到几何只能回退 1728 标「估算」）<br>时机：**每次重排之后**各上报一次（`ResizeObserver`/`resize`/旋屏/`fonts.ready`/样式变更/翻页重排；同屏 200ms 内防抖合并），并随周期 `state.report` 一起带。用途**只有一个**：控制台据此算「每行字数上限」——否则只能写死 1728，1280 屏上锁 24 会被显示端静默 `clamp` 回 18。它**不**替代 `online`（在线看 `presence`），也**不**替代 `pageMap`（分页摘要仍 7 字段）。
- **`retain=true` 的后果要写清**：`state` topic 长期保留最后一条，新接入的 Worker/控制台订阅即收到。故 ① 消费前必须先验 `dev/sig`（V2.3）再采信；② **不得**把它当作「设备此刻在线」的依据（在线看 `presence`）；③ 显示端离线时 retained `state` 仍是最后一条 `online:true`，控制台不许据此标在线。
- **`pageMap` 共 7 个字段 ＝ 6 标量 + `viewLines`**（`{anchor, unit, pageIndex, pageCount, sectionIndex, sectionCount, viewLines}`），只报摘要、不上报整张表（表可能几十 KB，5s 一条不可接受；`验收清单-V2.1` C7 有硬断言）。`viewLines` 为**首屏完整行数**（单个整数，语义见 §4.2）。任何文档写「6 标量」时必须补上 `viewLines`，否则与本节冲突。`pageIndex/pageCount` **恒为整章**屏序/屏数、`sectionIndex/sectionCount` **恒为整章**节序/节数，**两者都与 `unit` 无关**；`unit` 只决定**显示哪个、按什么步进**。切 `unit` 时两个分母都不变（否则页码会跳数，控制台会以为跳到了别的章）。`sectionIndex/sectionCount` **恒报**（`unit=page` 时也报），控制台据此显示"诗篇 23 · 节 3/6"并判断已到章末。
- 切 `unit` 时分母**不变**（V2.1.7 起；只有切章/切卷才会变）；`pageIndex` 不得当作持久状态，持久锚点只有 `{volumeId, chapterSn, verseSn, charOffset}`。
- `pageMap` 摘要自 **V2.2.3 定义、V2.2.5 起生效**（随 V2.1 一并落地，否则控制台拿不到节号）。控制台**不得**用 `floor` 公式自行估算屏数/行数（`N` 不是排版常数：段距 `1.1em` 让 `floor(高度÷行高)` 高估 40% 以上）

### 4.6 `display.style`：字段表 + 分页三参（V2.2.8 起定义）

服务端→显示端，`cmd`，QoS1，retain=false。`display.style` 自 V2.2.2 起被 §4.2 引用，但直到本版才在本文档里定义字段（此前是**悬空引用**：字段只在 `docs/样式下发指令-提案.md` 与 `前端设计-V2.1`）。

```json
{ "type": "cmd", "payload": { "kind": "style", "payload": {
    "fontSizePx": 72, "lineHeight": 1.75, "charsPerLine": "auto" } } }
```

| 字段 | 范围 / 步长 / 默认 | 语义 |
|---|---|---|
| `fontSizePx` | 24–160 / 4 / **缺省＝派生 `round4(视口高 × 6.7%)`** | 字号主控，px 直写 `--cds-font-size`；越界 `clamp(24,160)`，非 4 倍数**向下**取整。派生默认：720p **48** / 1080p **72** / 1440p **96** / 2160p **144**；派生结果必须进 `ack.effective`（服务端不知道屏高，**不得代算**） |
| `lineHeight` | 1.2–2.2 / 0.05 / **1.75** | 只改行高；**段距固定 `1.1em`（em = `fontSizePx`）**，故行距也在改「段距占几行」（1.75→0.63 行、1.2→0.92 行） |
| `charsPerLine` | **`"auto"` 或 6–40 整型 / 1 / 默认 `"auto"`（省略即 auto）** | 每行字数。`"auto"` ⇒ 显示端按 `N = clamp(6, 24, floor(W ÷ fontSizePx))` **自动派生**（`W = .body.clientWidth`；1920 宽扣左右 5vw＝1728px ⇒ 72px 时 N=**24**，正好满行）；显式整数 ⇒ 老师**锁定**，跨屏/跨字号不变，但受 `c × F ≤ W` 收紧（越界一律 `clamp`）。<br>**三个上限必须分清，不得混写成一个数**：① **硬约束** `c × F ≤ W`（算术，`floor(1728 / F)`：24px→72、72px→**24**、96px→18、120px→14、144px→12、160px→10）；② **`auto` 的可读性上限 24**——`auto` 永不返回 >24，即使 ① 允许 72（24px 字号那档）；③ **显式值的协议容错 ≤40**——为旧载荷/第三方客户端保留，UI 量程建议 **6–24**；显式传 25–40 时显示端仍接受（只要满足 ①），但 `ack.note` 应提示「超出可读性建议」 |
| `fontScale` | **作废** | **已作废（V2.2.13，产品 2026-11-18 12:44 宣布）**：收到一律**忽略**并在 `ack` 的 `note` 记 warn；**不得**再当乘数（乘两次 72×1.15=82.8，且越出 4 的步长网格）。旧载荷按「忽略 `fontScale`，沿用本机已生效 `fontSizePx`」处理 |

- **三参任一变更**：显示端必须**重排**并**重发 `pageMap`**；`pageCount`/`viewLines` 是「当前样式下」的量，样式一变旧值立即作废，不得跨样式复用；控制台只读上报、不得自算。原型缺这条（`kind==='style'` 只 `applyStyle`＋toast、不重算 `pages`）＝**验收必挂**。

- **字号默认也是派生量（V2.2.12，对齐产品 V2.1.11）**：`fontSizePx` 缺省时，显示端按 **`round4(视口高 × 6.7%)`** 派生（720p 48 / 1080p 72 / 1440p 96 / 2160p 144），显式下发时按 24–160／步长 4 收口。派生由**显示端**做，原因同 `charsPerLine`：服务端不知道屏高。这与「字号固定 72」的旧口径不同——旧口径在 4K 上只占屏高 5.56%，1080p 是 7.11%，同一个老师换屏就换观感。
  - **输入口径（V2.2.14 定稿：视口 CSS 高）**：按**视口 CSS 高**（`window.innerHeight`）派生——投屏全屏时等于屏高，与产品「按屏高派生」一致；窗口化预览（控制页同屏看）时按窗口高，会得到更小的字号，这正是分页应当跟着变的情形（§4.6 已定「`W`/三参任一变化都要重排重发 `pageMap`」）。**已定（V2.2.14）**：取视口高，不取物理屏高——CSS 只能知道 viewport，用物理屏高会在窗口化时溢出屏幕。控制台的预览区必须标注「**预览按窗口高派生，投屏以显示端实测为准**」，避免把预览字号当成投屏字号。**不得保留两套**（一套视口、一套物理屏），否则控制台预览与投屏会给出两套屏数，看起来像时基/分页 bug。
  - 派生字号与 `auto` 每行字数**互相咬合**：`F` 随屏高、`N = floor(W÷F)` 随屏宽，二者同比例 ⇒ 四档屏给出同一份分页（§4.6.3 表）。这不是巧合，是两条派生式同源的必然结果；但它仍受 `H÷F` 区间约束，见 §4.6.3 的边界。
- **`auto` 为什么是默认（V2.2.10，Jeremyzh 12:36 方案 A）**：投屏可能是 1080p / 2K / 4K，同一个字号在不同屏宽下的「合理每行字数」不同。固定 12 在 1080p 上只用到可用宽的 50%，在 2K 上更窄；`auto` 让**每行字数跟着字号与屏宽走**，老师不用先量屏。派生式在显示端算——**服务端不知道 `W`，不得替它算 `N`**。
- **上限 24 是可读性底线，不是技术限制（必须写清，否则下一轮会有人放开到 72）**：24px 字号下 `floor(1728÷24)=72`，技术上能排 72 字，但一行超 24 个全角字，后排视线跟行会跳行。所以 `auto` 的上限固定 24，与字号无关；**不要**把它改成 `floor(W÷F)` 的裸结果。
- **显式整数（老师手动锁定）**：锁定后跨屏、跨字号都不变——换到 2K 屏仍是这 40 字（若 `c × F > W` 则被 `clamp` 收到 `floor(W÷F)`）。锁定的代价是**跨屏一致性消失**：同一份文档在 1080p 与 2K 上的行数、屏数都会不同（§4.6.3 有对照）。
- **`c × F ≤ W` 只能由显示端执行**：服务端既不知道 `W` 也不知道 `F`，无法校验；`display.style` 的 `ack` 因此**必须回带生效值** `effective: {fontSizePx, lineHeight, charsPerLine}`（`auto` 回派生出的整数），否则控制台会以为请求生效了。`effective` 只出现在 `ack` 里，**不进 `pageMap`**（`pageMap` 恒 7 字段）。<br>**几何不进 `effective`，走 `state.report.layout`（V2.2.15 定稿，撤销 V2.2.14 的 5 字段版）**：`availW`/`availH` 随**每次重排**变化（换屏、旋屏、翻页重排、滚动条出现），与「是否刚下发过 `display.style`」无关；塞进 `ack` 只能覆盖「刚下发样式」这一种情形，且可能在重排完成前报到旧值。故两者分家：**`effective` ＝ 三条样式值的生效结果；`layout` ＝ 几何实测**。不得再把 `availW`/`availH` 塞回 `effective`（同一事实写两处，必然一边过期一边新，实现者无从取舍）。

- **控制台的「每行字数上限」必须用 `state.report.layout.availW` 算，不得写死 1728（V2.2.15）**：`c_max = min(24, floor(availW ÷ fontSizePx))`，`availW` 与 `fontSizePx` **必须取同一条 `layout`**（拿新宽度配旧字号会算出上限虚高）。写死 1920 屏的可用宽会在 1280/1640 屏上给出过大的上限——1280 屏 `availW≈1152`、72px 时真上限 **16**（`floor(1152÷72)`；V2.2.16 订正，原写 18 是 `floor(1728÷96)` 那行串档——照 18 实现会多排 2 字、行尾被 `overflow:hidden` 静默裁掉），控制台却允许选 24，显示端再 `clamp` 回 16，等于**锁了没生效**（静默改值，与「两次乘字号」同类错误）。同窗口的默认档另算：1280×800 派生字号 `round4(800×6.7%)=52`，`floor(1152÷52)=**22**`——**断言必须写清用哪档字号**（显式 72 ⇒ 16；默认 auto ⇒ 22），只写「1280 屏上限 18」两头都不对。控制台未连显示端时按 1920 估算，但必须标注「估算」。<br>**原型的承载方式（V2.2.16 备案，避免被读成「两套字段」）**：`prototype/display.html` 用 BroadcastChannel 的 `styleApplied`（＝`ack.effective`，三值）与 `layoutMetrics`（＝`state.report.layout`，五项）搬运同一结构，字段名与协议一致；上 MQTT 后分别落在 `ack.effective` 与 `state.report.layout`，**不是两套**。单屏/显控一体原型 `prototype/screen.html` 同样发 `layoutMetrics`（五项同形，200ms 防抖，V2.2.20），D-3 下控制台不必回退 1728。
- **`W` 或三参任一变化**（`ResizeObserver` / 旋屏 / 换屏）⇒ 重测 → 重算分页 → **重发 `pageMap`**。`auto` 模式下 `pageCount` 随屏变，控制台**不得缓存**旧值（缓存会在换屏后一直显示旧屏数）。

#### 4.6.1 分页模型（V2.2.8：算术为主线，DOM 为校验）

字体与可用宽都可能是变量（教室分辨率、字体 fallback），所以**行数不能靠浏览器折行得到**——中英数混排的宽度不同，同一段文字在不同字体下行数会变，分页表随之漂移。改为**先算行、再按行渲染**：

1. **字符宽度模型**：全角 = **1**，半角 = **0.5**（空白 0.5，零宽/控制字符不计）。
2. **行数（含续行缩进，V2.2.19 对齐产品 V2.1.15）**：每节**首行顶格**、字宽上限 `charsPerLine`；**节内折行（第 2 行及以后）与 `unit=page` 页切后的续行都缩 1 字符**，带缩进行有效字数 `c−1` ⇒ `L[k] = 1`（节字数_k ≤ `c`）否则 `1 + ceil((节字数_k − c) ÷ (c−1))`；`totalLines = Σ L[k]`；节首行号 = 前缀和。缩进是**样式**（`padding-left`，正文不插入任何字符、不影响字符宽度模型），但它**吃每行字数**——只加 `padding` 不减字数，续行必然横向溢出并被 `overflow:hidden` 裁掉（与 §4.6.2 的静默裁行同类）。
3. **渲染**：按 `L[k]` 切成**行数组**，每行一个 `white-space:nowrap` 块（行高 `lineHeight × fontSizePx`）。**不得**依赖浏览器自然折行：否则折行点随字体/字宽漂移，算出的行号与画出来的行对不上。行号从此是**数组下标**，`round(offsetTop ÷ 行高)` 这类换算不再需要（其 ±0.5 行残差问题随之消失）。
4. **装页规则（只有一条，V2.2.8 定死「整节下移」）**：从该页首行起逐节尝试——装得下就整节装入（每节**首次出现**时加 `1.1 × fontSizePx` 段距，**续写行不加**）；装不下且该节**自身**高度 ≤ 可用高 ⇒ **整节移到下一页**（不切）；该节**自身高于一屏** ⇒ 才在节内按行切分，页脚标「续」、下屏从切割点续写、**正文不插任何字符**。
   - **禁止「填满优先」**（把自身不到一屏的节切开以填满当屏）：同一份文档的 `pageCount` 与每屏行数会随实现者不同——诗篇 23、`charsPerLine=8`、72px 下整节下移 **5 屏**、填满优先 **4 屏**，属不可复用歧义。
5. **可用高/宽**：`H = .body 的 clientHeight`、`W = .body 的 clientWidth`，resize/旋屏后重测并**重算 + 重发 `pageMap`**（`ResizeObserver`）。`fontSizePx`/`charsPerLine` 缺省时还要用**视口高/宽**（`window.innerHeight` / `innerWidth`）派生（§4.6 字段表），所以它们也算输入。
6. **输出**：`pageCount` = 上述序列长度；`viewLines` = **首屏**行数。两者只由 `(fontSizePx, lineHeight, charsPerLine, H, W)` 决定（缺省参数先按视口派生再代入，派生规则见 §4.6 字段表），同一组输入必须得到同一组输出（可复现）。

#### 4.6.2 DOM 校验与溢出兜底（不得静默）

- **校验**：渲染后比对「算术页序列」与「实际行盒位置」（`Range.getClientRects()`）。不一致 ⇒ **字符宽度模型错了，是 bug**，必须显式告警（日志/`charsModelMismatch`），**不得**静默改用实测值覆盖——否则同一文档在两台设备上得到两套分页，控制台页码全错。
- **溢出兜底**：半角宽度 0.5em 只是近似（`W` 与 `i` 不等宽），某行 `scrollWidth > clientWidth` 时按实测重切该行、重算该屏，并上报该事件。行号仍是数组下标，协议形状不变。
- **不许半行裁切**：`overflow:hidden` 是按像素裁的，会在半行处横切。section 顶对齐与页尾都必须落在**整行**边界（末行 bottom ≤ H）。

#### 4.6.3 算例（诗篇 23，和合本 6 节 147 字，72px / 1.75 / H=902px（1080p 实测） / W=1728px）

节字数 `16/21/21/25/32/32`；行高 126px、段距 79.2px、整节下移。**含续行缩进**（V2.2.19 对齐产品 V2.1.15）：每节**首行顶格**、字宽上限 `c`；**节内折行（第 2 行及以后）与 `unit=page` 页切后的续行都缩 1 字符**，带缩进的行有效字数 ＝ `c−1` ⇒ `L(k) = 1`（节字数 ≤ `c`）否则 `1 + ceil((节字数 − c) ÷ (c−1))`。缩进是**样式不是字符**（`padding-left`，正文文本不插入任何空格），复制一段文本核对仍是原文：

| `charsPerLine` | 每节行数 | 总行数 | 屏数 | 每屏行数 |
|---|---|---|---|---|
| 8 | 3/3/3/4/5/5 | 23 | **5** | 6/3/4/5/5 |
| 10 | 2/3/3/3/4/4 | 19 | **4** | 5/6/4/4 |
| **12（手动锁定；V2.2.12 订正：默认已是 `auto`，12 只是手动档）** | 2/2/2/3/3/3 | 15 | **3** | **4**/5/6 |
| 14 | 2/2/2/2/3/3 | 14 | **3** | 4/4/6 |
| 16 | 1/2/2/2/3/3 | 13 | **3** | 5/5/3 |
| **24（1080p 下 `auto` 派生值）** | 1/1/1/2/2/2 | 9 | **2** | 5/4 |
| 40 | 1/1/1/1/1/1 | 6 | **2** | 4/2 |

**含缩进前后只差两格**：`c=8` 由 `20 行 5 屏 5/3/4/4/4` 变为 **`23 行 5 屏 6/3/4/5/5`**、`c=16` 由 `11 行 3 屏 5/4/2` 变为 **`13 行 3 屏 5/5/3`**；`c=10/12/14/24/40` 五行**逐字不变**（`c−1` 只在节字数刚好跨过整数格时才多出一行，这几档没有跨）。**六格屏数 5/4/3/3/3/2 亦全不变**——与产品 V2.1.15 的验收 B9 定稿表逐格一致。V2.1.12 的 `8→20/5`、`16→11/3` 是**无缩进**口径，已作废，不得再引用。

**`auto` 的派生值**：1920×1080、72px、`W=1728` ⇒ `N = clamp(6,24,floor(1728÷72)) = 24`。即**1080p 全屏下默认就是 24 字/行**（不是 12——V2.1.10 的默认 12 已作废，产品侧须同步；见 §4.6.5）。

**跨屏一致性（V2.2.10 红线）**：`auto` 下三档屏给出**同一份分页**：

| 屏 | 字号（派生默认） | `W`（扣 5vw×2） | `H`（实测可用高） | `H÷F` | 派生 `N` | 每节行数 | 总行数 | 屏数 | 每屏行数 |
|---|---|---|---|---|---|---|---|---|---|
| 720p 1280×720 | 48 | 1152 | 587 | 12.23 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |
| 1080p 1920×1080 | 72 | 1728 | 902 | 12.53 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |
| 1440p 2560×1440 | 96 | 2304 | 1217 | 12.68 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |
| 4K 3840×2160 | 144 | 3456 | 1847 | 12.83 | 24 | 1/1/1/2/2/2 | 9 | 2 | 5/4 |

（`H` 取**产品 V2.1.12 实测** `587/902/1217/1847`（`H = #content 纵高 − head/foot 绝对高`），比早期「纵高 ×0.9 − 61px」的估算值 `587/911/1235/1883` 各低 0/9/18/36px——两种口径下 `H÷F` 都落在同一区间、分页同为 9 行 2 屏 5/4，但**文档一律写实测值**，估算口径作废（估算会让人以为页眉页脚恒为 61px，实测 1080p 是 70px）。）

⚠️ **这条一致性的边界要写清，别当成定理**：`auto` **保证**的是「每行字数与屏宽同比例」（`N = W ÷ F`，故行数序列恒为 1/1/1/2/2/2）；**屏数**还取决于 `H ÷ F`，而 `H` 里含**绝对 px 的页眉/页脚**（不随屏缩放），所以 `H÷F` 并不严格同比例——四档实测区间是 `12.23`（720p）到 `12.83`（4K）。本例之所以四档同屏数，是因为「第 1 屏装下前 4 节」的判定区间很宽（`12.05 ≤ H÷F < 16.65`，即 `867.6px ≤ H < 1198.8px` 在 1080p 上），12.23–12.83 全落在里面。**这是区间余量，不是恒等**：1080p 实测 `H=902`，距下界 `867.6` 只有 **34.4px**——页眉页脚合计一旦比现在多 34.4px（即总高 > **104.4px**，现在是 70px），第 1 屏就少装一节、分页变 **3 屏（3/4/2）**，而 4K 的 `H÷F` 仍在区间内、仍是 2 屏——同一份文档在两种屏上屏数分叉。所以验收断言只能钉「同一 `H÷F` 区间内一致」，不能钉「任何屏都一致」；fixture 必须同时写死**窗口尺寸与页眉页脚高度**。

⚠️ **`charsPerLine=12` 时首屏是 4 行，不是 5 行**（默认 `auto` 在 1080p 派生 24，首屏才是 5 行）：前 3 节各 2 行，第 3 节要 `2×126 + 2×79.2 + 2×126 = 914.4px`，比实测 H=902 多 **12.4px** ⇒ 整节下移（原写「比 H=911 多 3.8px」两处都不准：914.4−911 应为 **3.4**，而文档一律按实测 902 判，V2.2.16 订正）。这个 12.4px 的边界说明 **fixture 必须写死 H（且写死宽）**，否则同一断言在不同页眉/页脚高度下翻屏。
- **⚠️ 窗口高不同 ⇒ 屏数不同，不是模型不一致（V2.2.13 备案）**：同一份诗篇 23、`c=12`、72px / 1.75 / 段距 1.1em，`H=581` 时是 **15 行 / 6 屏 2/2/2/3/3/3、首屏 2 行**（原型 12:47 在浏览器窗口内的实测，本文件 §4.6.1 的算法逐位复算一致）；`H=902`（1080p 实测）时才是 **3 屏 4/5/6**。`H=581` 的 `H÷F = 8.07` 落在 `12.05–16.65` 区间**外**，分叉是预期，**不是模型错**。**「6 屏」只能当「小窗口实测」，不得写进 fixture**；fixture 一律用本节 `H=902`（或写明自己的 `clientHeight`）。

⚠️ **「每节 2 行、一屏 5 行」这组数在任何一个 `charsPerLine` 下都不成立**（V2.2.10 订正）：`c=12` 时前 3 节各 2 行、首屏 **4 行**（第 4 节整节下移）；`c=24` 时每节 **1 行**、首屏 5 行。它是 Jeremyzh 11:47 的**示意**（视口 5 行、每节 2 行），不是默认参数下的真实分页，别当 fixture。

#### 4.6.4 已知缺口（V2.2.8 不解决，架构文档须备案）

- **无避头尾**：按字数硬切，行首可能出现「，。、）」等。若要，必须是**确定性状态机**且渲染与算术共用同一套规则，否则行数不可算。
- **半角宽度是近似**：靠 4.6.2 溢出兜底兜住，不做逐字形宽度表。
- **列宽语义：`auto` 下已不成为问题，显式锁定下仍未定**。`auto` 派生 `N = floor(W÷F)`，行宽 `N×F` **正好等于可用宽**（1920/72px ⇒ 24×72=1728），撑满即满行；只有老师**显式锁小**（如 `c=12`）时才出现「行宽 864px＝可用宽 50%，右侧留半屏空白」。**建议**：正文块宽恒等于 `charsPerLine × fontSizePx` 并**居中**——这样锁定小字数时是居中的窄栏（像诗页），auto 时自然满行。⚠️ 若块宽取「可用宽」而字数判定也按可用宽，24×72=1728 与 `W` 恰好相等，任何 letter-spacing／亚像素都会触发 §4.6.2 溢出兜底，届时应收 `N=floor(W÷F)` 或把块宽设为 `c×F`，不要靠 `overflow:hidden` 掩盖。
- **4K 电视常报 1920 CSS px（DPR=2）**：此时 `W`/`H` 与 1080p **完全相同**，`auto` 派生出的 `N` 也是 24，分页一致。**判定一律用 CSS px 的 `clientWidth/clientHeight`，不得按营销分辨率**（`screen.width` 报 1920 的 4K 机就是 1080p 行为；只有真报 3840 才落到 144px 那一档）。
- **`fontSizePx` 上限为什么必须到 144（V2.2.12 更正 V2.2.10 的「观感问题」说法）**：真 4K（`screen.width=3840` 的 CSS px）下 `W=3456`，而 `N` 的可读性上限是 24 ⇒ **满行（`c×F=W`）需要 `F = 3456÷24 = 144`**。若上限仍是 120，则 `c×F = 24×120 = 2880`，正文块只占可用宽 **83.3%**，两侧各留 **288px** 空白——这不是「字看着小」的观感问题，是**块宽填不满屏**的几何后果（本文件 V2.2.10 把它归为观感，错，此处更正）。所以协议范围放到 **24–160**：144 有推导（4K 满行值），160 只是上限余量（2160×6.7%≈144，160 留给更高屏）。**UI 必须能选到 144**，否则 4K 上 auto 永远满不了行；`F=144` 同样会让 `24×144=3456` 精确等于 `W`，§4.6.2 的溢出兜底在 4K 上与 1080p 同样适用，不得靠 `overflow:hidden`。
- **`fontScale` 已作废（V2.2.13）**：产品 2026-11-18 12:44 在 `样式下发指令-提案` 中宣布作废（字段表改为「作废、收到忽略并 warn」，`article.navigate.fontScale` 一并降级），本协议同步。至此「并存乘两次」的隐患闭合，实现侧只需支持 `fontSizePx`。

#### 4.6.6 「整章一屏」的三档顺序（V2.2.14，Jeremyzh 12:43 定）

「整章一屏」（`pageCount > 1` 时出现）＝把当前这一章压到一屏。**降档顺序写死，不得只降字号**：

1. **先降行距**：`lineHeight` 由当前值按 0.05 步长降到 **1.2** 为止；
2. **再把每行字数抬到上限**：`charsPerLine` 抬到 `min(24, floor(W ÷ F))`（`auto` 本已在上限，只有老师手动锁低时才有作用）；
3. **最后才降字号**：`fontSizePx` 按 4 的步长降，下限 24。

- 每降一档都要**重新分页并重发 `pageMap`**（§4.6 通则），控制台只读上报、不得自算；
- 三档都到最小值仍 `pageCount > 1` ⇒ **全部回滚**到点击前的三参，如实回报「已到最小（行距 1.2 / 字号 24）仍 N 屏，未改样式」——**不许留半套样式**（半套会让老师以为样式下发成功）；
- 改动生效后必须走 `ack.effective` 回报三值，控制台显示「生效 行距 x.xx / 字号 Npx / 每行 N 字」（`前端设计-V2.1` L398 现写「只降字号」，V2.1.12 须改；原型 `fitOnePage` 已按本顺序实现）。

## 6. 断线重连与降级

1. 重连间隔 3s / 6s / 12s / 24s，上限 5 次

## 7. 安全

- **目标态（出路 B，未实现）**：每台设备独立凭据，权限按 Topic 收敛（§1.3）。
- **现网实际（2026-11-18 12:27–12:29 实测复核，MQTT 5 over WSS）**：EMQX 只有**一组共享账密**。校验确实生效——错口令 `rc=134 Bad user name or password`、错用户名 `rc=135 Not authorized`（v3.1.1 编码即 4/5，与 10:54 首次实测一致，只是协议版本不同）；但校验的是那组**全站共享**的口令，`ClientID` 可任意伪造（用别人的 `cds-display-*` 连上去，先连者收到 `142 Session taken over` 被踢）。
  ⇒ **MQTT 连接本身不构成身份认证**（运维 R-14）。
- **比「ClientID 可伪造」更严重（同一批实测）**：现网 ACL 只拦根通配 `#` 与 `$SYS/#`，其余全放行。共享口令持有者可：① 订阅**全站**的 `cmd`/`state`/`ack`/`presence`（`cds/v1/+/*` 授予 QoS 1），读到每间教室在放什么、看到第几节；② 向**任意** `cds/v1/{任意 deviceCode}/cmd` 发布——**PUBACK 0 成功**，自订阅回环能收到，即**可越权指挥任意一块屏**；③ 向任意 `state`/`presence` 发布 **retain=true** 伪造状态——实测植入后，一个**全新订阅者**在订阅瞬间就收到这条伪造状态（测完已清空该 retained）。
  ⇒ **R-14 的性质是「可越权下发 + 可伪造上行 + 可污染 retained」，不只是「可伪造身份」**。因此：**任何安全结论都不得建立在 ACL 之上**；§1.3 的权限表是目标态。
- **两条由上面直接推出的业务硬约束**：① `playback_state` 只能由控制页 REST 播放控制写入，禁止由 `state.report.nowPlaying` 回写（否则一条伪造/过期的 retained report 就能改掉全站播放状态，见 §4.4）；② 显示端不得把「在 `cmd` 上收到消息」当作授权依据——V2.3 的 `srvSig` 未实现前，**下行没有任何链路级认证**。
- **现网的真实可信边界**：① Worker REST 的 JWT 校验（唯一身份来源）；② 上行 `dev/sig = HMAC_SHA256(key = devices.token_hash, msg = msgId|type|ts)`（V2.3）；③ 下行 `cmd` 的 `srvSig`（V2.3，Ed25519，私钥只在 Worker）。
  显示端**不得**假设「能在 `cmd` 上收到消息就说明是服务端发的」。
- 全链路 TLS（WSS）
- 消息体不含用户密码、设备密钥
- 单设备指令限流 20 条/秒，超限丢弃并回 `code=4029 rate_limited`

## 8. 错误码（ack.payload.code）

| code | 含义 |
|------|------|
| 4001 | 未知 type |
| 4002 | payload 字段缺失/非法 |
| 4003 | 不支持的音轨（**V2.1 起显示端不产生**：display 无 `<audio>`；码保留、不复用） |
| 4004 | 音频地址不可达（**V2.1 起显示端不产生**；码保留、**不得**改用作"投屏 URL 过期"，那是 4007——本文件 §4.3 曾误用，已改） |
| 4005 | 章节/经节不存在 |
| 4006 | 投屏内容超限 |
| 4007 | 投屏内容 URL 无效 / 预签名已过期（V2.3 新增；服务端重签后可重发） |
| 4008 | 已有其他音频锚点（另一终端正在播放，本端不得起播） |
| 4009 | 当前场景禁止起音乐（`cast`/`article` 下收到 `player.play` / `player.resume`） |
| 4029 | 限流 |
| 5001 | 显示端内部错误 |

> 同一条件在**两个面**各有一个码，别混：MQTT 下行回执用 **`4009`**；REST 用 **`4096` + HTTP `409`**（`api.md` §9，`error: "audio_blocked_by_scene"`）。`前端设计-V2.1-变更单` §2 写的「收到 `player.play` → 409」只适用 HTTP，**MQTT 侧不得回 `409`**（不是本协议的码）。
